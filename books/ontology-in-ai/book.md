## 前言：让概念、证据和动作连接起来

一个企业 AI 项目常常从自然语言提问开始：“这台设备为什么异常？”很快，问题就会延伸为：“你说的是哪台设备？读数来自哪个时点？适用的是哪个厂区的程序？谁能批准下一步？执行结果在哪里？”这些问题分别落在身份、时间、语义、权限和业务状态上。只增加模型参数，通常不能替我们确定这些边界。

本体提供了一种组织知识的方式。我们显式说明有哪些概念、对象之间是什么关系，以及某些陈述在给定语义下意味着什么。随后，数据工程把源系统记录映射进来，查询引擎获取事实，推理器计算特定语义下的蕴含，校验器检查输入是否符合约定，模型处理语言和不确定信息，动作服务控制真实修改。一个可靠系统来自这些能力的协作。

本书采用工程视角，重点不是记住术语，而是学会做出可检查的设计决定。例如：设备型号应建成类、实例，还是普通属性？“未查到维修记录”能否推出“从未维修”？OWL 的范围声明能不能拦截错误输入？模型给出一个合法 JSON，是否就可以写入知识库？这些问题需要具体分析，不能由“用了本体”一句话代替。

本书面向具备基础编程经验的 AI 工程师、数据工程师、FDE、解决方案架构师，以及需要审查技术方案的领域专家。读者不必先学会描述逻辑，但应能理解变量、函数、文件和简单数据库查询。

<a id="preface--一条贯穿全书的案例"></a>

### 一条贯穿全书的案例

我们使用“设备维修助手”作为贯穿案例。两个合成租户都存在编号为 `P-101` 的设备，设备分属不同厂区；温度源数据使用两种单位；程序文档具有访问范围和有效期。系统需要找到正确对象，读取适用事实，取得有权使用的程序，再形成供人审核的建议。

首期唯一外部业务动作是**创建维修工单草稿**。草稿要绑定具体设备、对象版本、程序及证据，经具有权限的人批准后，才能交给模拟业务系统。系统不控制设备启停，也不将草稿创建解释为故障已经修复。

案例故意保留常见的困难：同名对象、单位转换、缺失记录、错误数据、越权访问、文档中的恶意指令、批准后状态变化，以及外部操作成功但响应丢失。掌握这些分支，比只跑通一次正常问答更接近实际工程。

### 书与教程怎样配合

章节解释原理和取舍，教程提供可执行材料。教程使用 Python、RDFLib、OWL-RL、pySHACL 和 JSON Schema 校验器。依赖版本固定，数据保存在仓库内，核心流程可以在没有商业平台账号、没有模型服务的情况下运行。

### 关于证据与版本

本书以 W3C 的 RDF 1.1、RDFS、OWL 2、SPARQL 1.1 和 SHACL 等文档为主要语义依据。这是教程的明确基线，不表示这些名字之外没有新标准或扩展。工具的具体实现能力、默认配置和版本支持仍需另外核对。

## 第 01 章　本体为什么对 AI 有用

本章目标是建立一个可用于选型的判断：当 AI 缺少稳定的业务含义时，本体能提供什么；当问题主要来自其他环节时，本体为什么未必是优先投入。

<a id="ch01--11-从一句含糊的话开始"></a>

### 1.1 从一句含糊的话开始

“P-101 温度异常，帮我处理。”这句话省略了许多前提。`P-101` 是否全公司唯一？“温度”测量的是轴承、介质还是电机外壳？“异常”依据哪个程序和阈值？“处理”是检索说明、生成建议、创建草稿，还是控制设备？人类同事常常借助共同环境补齐这些信息，模型却可能把不同资料中的同名对象拼在一起。

本体建模把这些隐含区分变为显式结构：设备是一类对象，观测是另一类对象；观测关联被观察设备，包含数值、单位和时间；设备关联适用程序；执行动作有独立的输入和前提。这样，系统能够通过标识、关系和规则获取上下文，而不用每次完全依赖语言猜测。

用工程语言说，本体是对一个领域中概念、关系及相关语义的显式建模。具体项目可以采用轻量词汇和领域模型，也可以采用有形式语义的 RDF、RDFS、OWL。本体工程并不要求所有系统使用同一种存储产品，也不要求第一天就构造完整的企业知识模型。[R05](#references--r05) [R38](#references--r38)

<a id="ch01--12-把容易混用的概念分开"></a>

### 1.2 把容易混用的概念分开

| 概念 | 主要回答 | 对设备案例的贡献 |
| --- | --- | --- |
| 数据库模式 | 怎样组织和存储记录 | 定义设备表、观测表、主键和索引 |
| 数据字典 | 字段按什么口径解释 | 说明温度单位、时间含义、状态枚举 |
| 分类体系 | 项目怎样分组和层级排列 | 把泵分成不同类型 |
| 本体 | 概念与关系具有什么可共享的语义 | 说明泵属于设备、观测针对某个对象、关系如何推导 |
| 知识图谱 | 怎样用图组织领域事实和知识 | 存放具体设备、观测、程序及其连接 |
| 图数据库 | 怎样高效保存和查询图 | 执行邻接遍历、关系查询或相应查询语言 |
| 向量表示 | 内容在某种模型下怎样相似 | 找到措辞不同但语义相关的说明段落 |
| RAG | 怎样取得外部证据来辅助生成 | 把适用事实和手册送给模型 |

这些能力可以组合。一个知识图谱可以只有简单的实体和关系，也可以包含丰富的形式语义。一个图数据库不会因节点被叫作“类”就自动实现 OWL 推理。一个本体也可以服务于关系数据库之上的业务接口，而无需把全部数据迁入同一个三元组存储。[R01](#references--r01) [R28](#references--r28)

<a id="ch01--13-本体对-ai-的五种作用"></a>

### 1.3 本体对 AI 的五种作用

**统一对象身份。** 模型在回答之前，先知道自己面对的是哪家企业、哪个厂区的哪台设备。名称用于帮助人阅读，标识负责连接记录。这可以减少同名对象被错误合并的问题，但实体匹配规则仍要实际实现。

**组织检索路径。** 用户说出设备编号时，系统可沿“设备使用程序”取得相关手册，而不仅在全文中搜索编号。关系帮助找到证据，证据是否足够以及是否有权使用仍需继续检查。

**限定输出与工具含义。** 模型输出的 `asset_id`、`procedure_id` 和动作名称有明确业务意义。服务可以检查对象是否存在、程序是否适用、参数是否一致，而不是接收一段无法复核的自由文本。

**支持特定逻辑推理。** 已知离心泵属于泵，泵属于设备，可以在相应规则下推出某台离心泵也是设备。这个结论不依赖模型的语言流畅度。它也不能顺便证明该设备安全、故障或可操作。

**形成可复用的业务接口。** 当多个应用和模型使用同一套对象与动作定义时，客户更容易复用查询、界面、规则和评估案例。Palantir Ontology 将对象、属性、关系、动作等组合为组织运营层，是这种工程路线的一种平台化实现。[R33](#references--r33) [R34](#references--r34)

<a id="ch01--14-本体不能替系统承担什么"></a>

### 1.4 本体不能替系统承担什么

一套语义模型不能保证输入记录真实。若温度传感器校准有误，给读数加上正确类型仍不会修复测量。关系完整也不代表因果关系成立：“温度高”和“轴承损坏”之间，需要领域证据，而不是在图中画一条边就能确定。

本体文件不会自动实施用户权限。即使图中记录了“甲用户属于北厂”，应用仍须把可信登录身份交给权限检查，再限制查询、模型上下文和业务动作。同样，OWL 推理器的输出不会自动更新工单系统，也不会代替人工批准。

模型的幻觉也不会因为读取过本体就消失。模型仍可能引用不存在的证据、误解关系方向或生成合法但错误的字段。工程系统必须检查生成结果，并允许“信息不足”成为有效结果。

这些边界可以用一条责任链表示：

`业务语义 → 有来源的数据 → 授权查询 → 模型或规则 → 验证 → 批准与执行 → 回执与评估`

链上每个箭头都可能出错。设计时应能指出每一层由哪个组件负责，而不是把整条链统称为“知识图谱能力”。

<a id="ch01--15-什么情况下值得引入本体"></a>

### 1.5 什么情况下值得引入本体

本体通常更适合以下情况：多个系统反复描述相同业务对象；同名字段存在不同口径；问题依赖对象间关系；多应用需要共用业务含义；模型输出要连接明确动作；概念和规则需要由领域专家共同维护。

如果资料规模很小、几乎没有跨系统对象、只需查询一份静态手册，维护本体可能暂时没有足够收益。可以先建立文档结构、访问规则和评估集，再看失败是否来自语义不一致。这个选择不是成熟度竞赛，而是投入产出判断。

开始前提出一个可以验证的假设，例如：“通过设备到程序的显式关联，可以减少因手册未写设备编号而漏检的案例。”把它与关键词检索、普通向量检索或简单规则方案比较。只有实际减少错误、减少维护工作或支持必要能力，才算获得了相应价值。

<a id="ch02--第-02-章-从业务问题到能力问题"></a>

## 第 02 章　从业务问题到能力问题

本章目标是把“建设知识图谱”改写为有范围、输入和预期结果的工程任务。建模开始前，先确定系统必须回答哪些问题，以及哪些问题当前不回答。

<a id="ch02--21-能力问题是模型的验收入口"></a>

### 2.1 能力问题是模型的验收入口

能力问题（competency questions）是知识库应当能够回答的问题集合。Noy 与 McGuinness 用它们帮助确定领域范围，并在后续检查模型是否包含必要信息。[R38](#references--r38)

“系统要理解设备”很难验收。“北厂当前有哪些温度超过本教学阈值、且存在有效程序的设备？”就可以继续拆解：北厂如何确定，温度取哪个时点，阈值来自什么规则，程序有效期怎样检查，当前用户能否读取结果。问题中的每个限定词都可能对应一种数据、关系或约束。

我们为贯穿案例定义以下问题：

| 编号 | 能力问题 | 必须依赖的知识 | 预期失败方式 |
| --- | --- | --- | --- |
| CQ-01 | 当前用户说的 P-101 是哪台设备 | 租户、设备标识、区域权限 | 无法唯一定位时要求澄清或拒绝 |
| CQ-02 | 该设备最新可用的温度是多少 | 观测、单位、时间、数据来源 | 缺失、冲突或过期时说明原因 |
| CQ-03 | 应读取哪个检查程序 | 设备到程序的关系、文档版本与权限 | 不返回无权或已失效程序 |
| CQ-04 | 已知类型和关系能推出哪些事实 | 类层级、逆属性、传递属性 | 不把未声明事实擅自当成假 |
| CQ-05 | 能否创建一份维修工单草稿 | 当前身份、批准、版本及业务前提 | 不满足条件时阻止写入 |
| CQ-06 | 上次超时的创建请求结果如何 | 稳定请求 ID、回执、对账记录 | 保留未知状态，先查询而非重复创建 |

这些问题覆盖语言、数据、推理和动作。最后两项不能单靠本体文件实现，却会反过来影响对象设计：没有提案、批准和执行记录，就无法清楚回答它们。

<a id="ch02--22-从问题倒推最少知识"></a>

### 2.2 从问题倒推最少知识

以 CQ-02 为例，直接在设备对象上放一个 `temperature` 属性看起来最简单，但它丢失了“谁在何时观察了什么”。如果设备有多个传感器、读数持续变化或需要追溯，观测应成为独立实体，并关联设备、数值、单位和时间。

不要机械地把每个字段都建成实体。只有当某项内容需要独立身份、多个属性、多种关系或生命周期时，独立对象才更有价值。温度单位可以在早期使用有限受控词汇，设备序列号可以是属性，维修事件则通常值得拥有身份和时间。

问题分析可以采用四步：

1. 写出问题的输入和使用者，例如“北厂计划员 + 设备编号”。
2. 写出正常情况下应返回的内容，例如“设备名称、温度、时点、程序和证据”。
3. 写出必要依据，例如“源系统版本、单位转换规则、程序有效期”。
4. 写出无法回答时的行为，例如“不使用零填补缺失温度，不从其他租户补齐”。

结果应是一份小型语义合同。它同时约束数据接入、查询、模型输出与验收，后续不应只保留最初的流程图。

<a id="ch02--23-把问题变成可执行断言"></a>

### 2.3 把问题变成可执行断言

CQ-01 至少可以变成两条检查：北厂甲公司身份查询 `P-101`，应得到甲公司的北厂循环泵；同一身份不能读到乙公司的同编号设备。这里的验收不是“返回了一个设备”，而是“在可信身份范围内返回了正确设备”。

CQ-02 的正常输入是 `92.0 C` 和带时区的观测时点。边界案例包括 `161.6 F`、未知温标、没有记录、同一时点存在冲突记录，以及超出新鲜度门槛的旧数据。正常、异常和边界共同定义能力。

CQ-04 可以采用一条精确断言：在加载本体并运行相应推理后，`P-101 rdf:type Asset` 为可推出事实。对应的反例是：没有维修记录，并不能在开放世界语义下推出“从未维修”。用一正一反的检查，能避免把推理理解成任意补全。

CQ-05 应检查业务系统的实际效果：一次有效请求只产生一份草稿，回执指向正确设备。模型回答“已经创建”不是验收证据。CQ-06 则需要模拟外部系统成功、响应丢失的情况，检查恢复流程不会再创建第二份草稿。

<a id="ch02--24-用反例暴露建模歧义"></a>

### 2.4 用反例暴露建模歧义

本体评审最有价值的材料，往往是会令两个人给出不同答案的具体案例。例如：设备迁厂后，其旧观测属于旧厂还是新厂的访问范围？两个系统都叫“运行中”，一个表示有电，一个表示正常产出，它们能否共用一个状态？维修程序适用于某种型号，是否也适用于后来改造过的同型号设备？

解决这些问题时，先写出业务选择，再把选择落实为字段、关系、时间或策略。未作决定的地方应记为待决事项，避免用模糊术语掩盖分歧。

| 建模决定 | 需要记录的理由 | 后续验证 |
| --- | --- | --- |
| 设备标识包含租户范围 | 编号只在租户内部唯一 | 同编号跨租户测试 |
| 观测具有独立身份和时间 | 支持历史、冲突及测量来源 | 重复与乱序导入测试 |
| 程序通过明确关系关联设备 | 文档不必逐一写入设备编号 | 关系检索与全文检索对照 |
| 创建草稿是独立动作 | 审核、正式派工和修复另有流程 | 回执与副作用数量检查 |

<a id="ch02--25-管理范围和责任"></a>

### 2.5 管理范围和责任

首期项目可以只覆盖一个设备类别、一类异常和一种草稿动作。这是为了让数据、规则、界面和运行责任同时成立，不是限制未来的模型规模。

每个能力问题最好指定业务解释人、数据负责人和工程验收人。领域专家决定“怎样才算正确”，数据负责人说明事实在哪里、多久更新，工程师把定义变成可重复的检查。若业务定义改变，相应的数据约束、查询和评估也必须变化。

保留一份未纳入范围的问题清单同样重要。例如“根据声音诊断具体故障”可能需要音频、标注数据和专门模型；“自动停机”涉及设备控制与行业安全要求。这些能力不能因现有对象已经叫作 `Asset` 就被默认包含。

<a id="ch02--思考题"></a>

### 思考题

1. “找出所有没有维修过的设备”为什么需要比“找出已登记维修事件的设备”更多的前提？请写出所需的数据完整性条件。
2. 把“帮销售理解客户”改写为三条能力问题，并为每条写出正常答案和一个应拒答或澄清的情况。

配套练习见[教程第 01 课](#lesson01)，其中的数据和身份对应本章的 CQ-01 至 CQ-06。

<a id="ch03--第-03-章-rdf标识与图数据"></a>

## 第 03 章　RDF、标识与图数据

本章目标是理解 RDF 的最小结构，并能够解释标识、字面量、空白节点和命名图各承担什么职责。只有这层含义稳定，后续推理和 AI 上下文才有明确对象。

<a id="ch03--31-三元组表达一条关系"></a>

### 3.1 三元组表达一条关系

RDF 1.1 用主语、谓语、宾语组成三元组。主语可以是 IRI 或空白节点，谓语必须是 IRI，宾语可以是 IRI、空白节点或字面量。RDF 图是三元组的集合；集合中重复添加同一条三元组，不会因此记录“发生了两次”。[R01](#references--r01)

下面是一段可以独立解析的 Turtle：

```turtle
@prefix ex: <https://example.org/maintenance/> .
@prefix d: <https://example.org/data/TENANT-A/asset/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

d:P-101 a ex:CentrifugalPump ;
    ex:assetId "P-101" ;
    ex:version 7 ;
    ex:asOf "2026-09-01T09:00:00Z"^^xsd:dateTime .
```

`a` 是 `rdf:type` 的 Turtle 缩写，表示实例的类型。分号沿用同一主语，句点结束一组语句。前缀只是长 IRI 的书写缩写，改变前缀名而保留展开后的 IRI，不会改变标识；改变 IRI 本身则可能改变对象。[R02](#references--r02)

图中的一条三元组是陈述，不是操作命令。`P-101 usesProcedure PROC-PUMP-01` 表示关联，不能据此认为程序已经执行。维修发生一次，应另建有身份和时间的事件或工单，不能用重复插入这条关联来计数。

<a id="ch03--32-标识与名称承担不同职责"></a>

### 3.2 标识与名称承担不同职责

`"P-101"` 是字符串；`https://example.org/data/TENANT-A/asset/P-101` 是一个 IRI。前者可以作为资产标签，后者用于连接图中的对象。两个租户都拥有 `P-101` 时，IRI 中的租户范围使它们保持不同的资源标识。

本书的示例域名 `example.org` 用于教学，不代表真实设备服务。IRI 不一定需要在运行时访问网络才能使用。是否可解引用、解引用返回什么、访问时需要何种权限，都属于另外的发布与运行约定。[R01](#references--r01)

身份设计至少要回答：标识在什么范围内唯一，由谁分配，什么时候可以变更，旧标识如何迁移，外部系统 ID 如何映射。不要把会变化的名称、当前所属部门或模型猜出的描述直接当作长期主键。

在设备迁厂的场景中，设备通常仍是同一台物理设备，所在厂区是会变化的关系。若把厂区名称直接写进不可变身份，迁厂就可能被错误实现为“删除旧设备、创建新设备”。是否包含区域，应根据编号制度和实体生命周期决定；本教程的长期标识只包含租户、实体类别和稳定编号。

<a id="ch03--33-字面量必须保留类型语言和单位"></a>

### 3.3 字面量必须保留类型、语言和单位

`"92"`、`92` 和 `"92"^^xsd:decimal` 的表达不完全相同。第一个是字符串形式，第二个在 Turtle 中是整数字面量，第三个声明十进制数据类型。解析、比较和校验依赖这些语义，不能只看打印出来的数字像不像。[R01](#references--r01) [R02](#references--r02)

语言标签适合区分名称：`"循环泵"@zh` 与 `"circulation pump"@en` 可以共同描述同一设备。它们不会自动变成不同的设备。反过来，名称相同也不保证对象相同。

数值的数据类型不会说明测量单位。即使两个值都使用 `xsd:decimal`，摄氏度和华氏度仍不能直接比较。本教程将源数据 `161.6 F` 转成 `72.00 C`，再将标准化值与单位一起保存。未知温标应触发错误，而不是选择一个看起来合理的解释。

当资料包含“约 90 度”“高于 90 度”或测量区间时，不应一律压成精确数值 90。可以保留上下界、比较关系、不确定性与原始文本。模型抽取时也应尊重这些差别。

<a id="ch03--34-空白节点适合局部结构"></a>

### 3.4 空白节点适合局部结构

空白节点表示没有给出全局名称的资源。Turtle 中的 `[]` 常用于表达局部限制或结构，例如一个 SHACL 属性形状。空白节点标签通常只在相应序列化或处理上下文中有意义，不适合作为对外业务 API 的稳定设备 ID。[R01](#references--r01)

如果一个对象需要被用户收藏、从别的系统引用、反复更新或追溯，就应认真考虑为它分配稳定 IRI。临时图中的一个中间结构则不一定需要全球命名。

还有一个容易忽略的后果：同一 RDF 图可以有不同的合法序列化，空白节点标签也可能不同。因此，“两个 Turtle 文件的 SHA-256 不相同”并不能直接证明图的语义不同。原始文件哈希适合识别文件版本；需要规范化 RDF 数据集时，应采用对应的规范化方案并了解其范围。[R40](#references--r40)

<a id="ch03--35-命名图组织数据不自动授予权限"></a>

### 3.5 命名图组织数据，不自动授予权限

RDF 数据集包含默认图以及零个或多个命名图。TriG 可以序列化这种结构。[R01](#references--r01) [R11](#references--r11)

```trig
@prefix ex: <https://example.org/maintenance/> .
@prefix g: <https://example.org/graph/> .
@prefix a: <https://example.org/data/TENANT-A/asset/> .
@prefix b: <https://example.org/data/TENANT-B/asset/> .

g:TENANT-A { a:P-101 ex:assetId "P-101" . }
g:TENANT-B { b:P-101 ex:assetId "P-101" . }
```

命名图可以用来组织来源、租户或版本，但图名本身没有访问控制魔法。若查询服务允许用户执行 `GRAPH ?g` 并遍历所有图，数据仍可能全部返回。本教程把可信身份映射到允许的图，并继续检查区域；模型不直接获得任意数据集查询权限。

默认图是否是其他图的联合视图，也不能靠猜。不同数据集构造方式、数据库配置和查询协议可能有不同安排。本教程显式设置 `default_union=False`；面向用户的服务在确定的图上执行参数化查询。

<a id="ch03--36-rdf-与-json-ld"></a>

### 3.6 RDF 与 JSON-LD

JSON-LD 通过上下文将 JSON 中的术语映射到 IRI，并表达类型、标识及图结构。普通 JSON 不会因为字段名看起来像业务对象就自动具备同样的 RDF 语义。[R12](#references--r12)

JSON-LD 适合与 JSON 应用交换图数据，但远程 `@context` 也可能引入网络依赖。解析不可信材料时，需要约束可访问的文件和网络资源。RDFLib 文档明确提醒，远程上下文和 SPARQL 联邦查询可能触发外部访问。[R39](#references--r39) 本教程的基础导入仅处理仓库内受控文件。

<a id="ch04--第-04-章-rdfsowl-与逻辑推理"></a>

## 第 04 章　RDFS、OWL 与逻辑推理

本章目标是准确解释“推理”一词。形式推理是在给定语义和前提下计算蕴含，不等于模型写出一段像推理的文字，也不等于任意预测缺失的边。

<a id="ch04--41-从类层级开始"></a>

### 4.1 从类层级开始

如果我们知道离心泵是泵的一种，泵是设备的一种，而且 P-101 是离心泵，那么在 RDFS 语义下可以推出 P-101 也是泵和设备。[R04](#references--r04)

```turtle
@prefix ex: <https://example.org/maintenance/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

ex:CentrifugalPump rdfs:subClassOf ex:Pump .
ex:Pump rdfs:subClassOf ex:Asset .
ex:P-101 a ex:CentrifugalPump .
```

推理器可以将得到的类型显式加入一个派生图，也可以由查询引擎按相应蕴含规则回答。前者常称物化，后者可能采用查询重写等方式。选择哪种方式，会影响查询速度、更新成本以及派生事实失效时的处理。

本教程复制原始图，再用 OWL-RL 做规则闭包，保留“原始三元组”和“闭包三元组”的区别。增加了多少三元组只是运行现象，不是知识质量评分，其中可能包含标准词汇相关的公理性结果。

<a id="ch04--42-domain-与-range-不是表单验证规则"></a>

### 4.2 domain 与 range 不是表单验证规则

考虑下面的声明：

```turtle
@prefix ex: <https://example.org/maintenance/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

ex:hasObservation rdfs:domain ex:Asset ;
                  rdfs:range ex:Observation .
ex:MysteryObject ex:hasObservation ex:Reading-1 .
```

RDFS 可以据此推出 `MysteryObject` 属于 `Asset`，`Reading-1` 属于 `Observation`。它通常不会因为主语原先没有写 `a Asset` 就拒绝输入。这正是语义推导与数据约束的区别。[R04](#references--r04)

如果同一个属性有两个 domain，通常意味着使用该属性的主语同时属于两个范围类，而不是“二选一”。把业务表单中“可选设备或产线”的想法直接翻译成两个 domain，就可能获得与预期不同的类型结论。

因此，声明关系含义和检查输入完整性应分别设计。下一章的 SHACL 负责检查所给图中的节点是否符合约定形状。

<a id="ch04--43-owl-增加了哪些表达能力"></a>

### 4.3 OWL 增加了哪些表达能力

OWL 2 提供比基础 RDFS 更丰富的类表达式和公理，可以表达类的交、并、补、等价、不相交，个体的相同或不同，以及属性的逆向、传递性、特定基数限制等。不同语言子集和推理任务的实现要求不同。[R05](#references--r05) [R06](#references--r06)

在设备案例中，`partOf` 表达组成关系并声明传递性。已知设备属于产线，产线属于厂区，就能在该建模约定下推出设备属于厂区。`hasPart` 作为它的逆属性，则支持从厂区或产线看组成对象。

不能把所有关系都声明为传递。例如“直接连接”“本次审批人”“最近一次维修”通常不能任意沿链传递。属性是否传递来自领域语义，不来自“希望一次查到更多节点”的实现愿望。

等价也需要谨慎。`owl:sameAs` 表示两个名称指向同一个体，影响的是相关陈述的整体替换，而不只是“名字有点像”。同型号的两台泵绝不能因此设为 sameAs。产品型号与实物设备也不是同一层次的对象。

<a id="ch04--44-开放世界与不同名称"></a>

### 4.4 开放世界与不同名称

OWL 常采用开放世界假设：没有被知识库陈述或推出的事实，可能仍然为真。没有查到维修事件，并不自动推出设备从未维修。可能是旧系统尚未接入，也可能是记录延迟。[R06](#references--r06)

这与应用中的操作规则可以共存。维修草稿服务可以规定：“如果当前请求缺少可信批准记录，就拒绝执行。”这里是服务对可执行条件作出的明确约定，不是宣称在宇宙中绝不存在批准。

OWL 也不默认不同名字必然指向不同个体。如果某属性具有函数性，一个对象连接到两个不同名称的对象，推理可能要求这些名称指向同一个体，而不是立即报告表格式的重复值错误。只有结合额外的不同个体声明、数据类型语义或其他公理，才可能得到不同结论。[R06](#references--r06)

这也是为什么“设备只能有一个责任人”的业务规则不应只靠一个 `owl:FunctionalProperty` 声明。业务数据通常还需要一个 `sh:maxCount 1` 之类的约束，并明确当前责任人与历史责任关系的区别。

<a id="ch04--45-存在性不保证出现可查询的新名称"></a>

### 4.5 存在性不保证出现可查询的新名称

OWL 可以表达“每台某类设备至少有一个某类组件”。在开放世界下，缺少显式组件记录并不总构成矛盾：模型的解释中可以存在尚未命名的组件。

读者应区分三件事：逻辑上要求某物存在，推理器是否生成相应内部结构，以及应用是否获得一个可以查询和操作的业务 ID。它们不是同一回事。需要用户查看组件序列号、安排维修或核对台账时，仍然要有明确的数据记录和完整性约束。

<a id="ch04--46-选择适当的推理范围"></a>

### 4.6 选择适当的推理范围

| 选择 | 适合的关注点 | 需要核对 |
| --- | --- | --- |
| RDFS | 基础类型、属性和层级蕴含 | 是否启用推理，查询是否看得到派生类型 |
| OWL 2 EL | 大规模类体系中某些高效推理任务 | 语言表达限制及具体推理器支持 |
| OWL 2 QL | 面向关系数据访问的特定表达范围 | 查询重写、数据映射和系统实现 |
| OWL 2 RL | 可以规则化实现的一组 OWL 表达 | 输入是否落在所需范围、数据类型与规则实现 |
| OWL 2 DL 推理器 | 更丰富的描述逻辑表达与推理任务 | 可判定范围、性能及不一致处理 |
| 自定义业务规则 | 阈值、流程前提、时间与业务判断 | 规则版本、优先级、异常及来源 |

OWL 2 Profiles 是对语言子集的规范说明，不能只凭名字推断某个工具对所有输入完整、快速或一致。[R07](#references--r07) Apache Jena 与不同图平台提供各自的推理配置和实现范围，也应逐一核对。[R21](#references--r21)

本教程使用 OWL-RL 的规则物化，验证类层级、逆属性和组成关系传递。它不提供完整 OWL 2 DL 推理，不将所有矛盾诊断能力作为已实现功能，也不生成完整证明树。生产系统若要求解释“这条结论由哪些公理导出”，需要另外设计推导来源或使用具备对应解释能力的工具。[R19](#references--r19)

<a id="ch04--思考题"></a>

### 思考题

<a id="ch05--第-05-章-shacl-与数据质量"></a>

## 第 05 章　SHACL 与数据质量

本章目标是为进入 AI 和动作系统的数据建立明确的检查方法。一个图能被解析，或者在某种语义下没有发现矛盾，都不足以说明它满足业务使用要求。

<a id="ch05--51-从有意义进入可使用"></a>

### 5.1 从“有意义”进入“可使用”

假设一个设备只有名称，没有版本，也没有新鲜观测。它仍然可以是一张合法的 RDF 图，但当前工单服务无法判断批准之后设备是否变化，模型也无法可靠解释当前温度。

SHACL 用形状描述所给数据图应满足的条件，包括值的类型、数量、范围、关系以及其他检查。标准区分数据图和形状图，验证结果通过符合性与具体结果节点表达。[R08](#references--r08)

本教程对设备要求标识、租户、区域、版本、状态和事实确认时间；对温度观测要求目标设备、数值、标准化单位和时间。这些不是全世界所有设备本体都必须遵守的公理，而是本应用的输入合同。

<a id="ch05--52-一个最小属性形状"></a>

### 5.2 一个最小属性形状

```turtle
@prefix ex: <https://example.org/maintenance/> .
@prefix sh: <http://www.w3.org/ns/shacl#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

ex:AssetVersionShape a sh:NodeShape ;
    sh:targetClass ex:Asset ;
    sh:property [
        sh:path ex:version ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:datatype xsd:integer ;
        sh:minInclusive 1
    ] .
```

这个形状依次回答：检查哪些节点，沿哪个属性取值，至少和至多有几个值，值应是什么类型，允许的最小值是多少。若节点没有版本，`minCount` 可以报告问题，而不会自动造出一个版本号。

`sh:class` 检查值节点是否符合要求的类型关系，`sh:in` 可以限定一组值，`sh:pattern` 可以检查字符串形式，属性路径可以表达更复杂的连接。具体采用哪些能力，应根据校验器版本和数据规模决定。[R08](#references--r08)

<a id="ch05--53-目标选择与推理配置必须写清"></a>

### 5.3 目标选择与推理配置必须写清

只定义正确约束还不够，必须确认预期节点真正成为验证对象。例如，`sh:targetClass ex:Asset` 如何处理 `CentrifugalPump` 实例，取决于数据图中是否有相应类型与子类信息，以及使用的 SHACL 类型规则。

SHACL 标准的类实例判定会考虑图中的 `rdfs:subClassOf` 链，不能简单声称“没有额外推理就只检查直接类型”。但它也不会无条件执行所有 OWL 公理。特别是某些通过 domain、range 或其他表达才能推出的类型，必须明确数据准备和推理设置。[R08](#references--r08)

本教程给 pySHACL 提供本体图与形状图，显式使用 `inference="rdfs"`。同时用一份故意错误的输入检查：缺少版本、温度值是字符串 `"hot"`、温标没有标准化。这样，我们验证的是实际配置下的行为，而不是只看工具页面说它支持 SHACL。[R20](#references--r20)

<a id="ch05--54-闭合形状与完整世界是两回事"></a>

### 5.4 “闭合形状”与完整世界是两回事

`sh:closed true` 可用于限制目标节点出现的属性，配合 `sh:ignoredProperties` 允许某些例外。它并不等于宣布整个业务世界已经完整，也不是开启一个通用的闭世界推理模式。[R08](#references--r08)

过早关闭全部属性可能让来源注释、血缘信息或兼容性扩展都变成错误。应用可以对关键命令使用严格的字段白名单，对知识图谱节点保留受控扩展。选择必须服务于明确风险，而不是把“越严格”自动视为“越正确”。

同样，`sh:minCount 1` 能说明本次所给图里缺少必要值，不能证明现实世界没有那个值。验证报告应被解释为“当前数据不能进入此流程”，而不是对现实作出未经支持的结论。

<a id="ch05--55-哪些检查应放在哪里"></a>

### 5.5 哪些检查应放在哪里

| 检查 | 合理位置 | 原因 |
| --- | --- | --- |
| 记录是否能解析、字段是否存在 | 导入层 | 尽早隔离坏记录 |
| 数值类型、数量、关系与单位 | SHACL 或等价数据合同 | 形成可复用的图数据检查 |
| “超过 80 度应进入核查” | 有版本的业务规则 | 阈值属于本场景政策，并非普遍设备真理 |
| 数据是否超过 300 秒 | 请求时的服务检查 | 依赖当前时钟，静态通过会随时间失效 |
| 用户能否处理该设备 | 授权服务 | 依赖可信身份和当前权限 |
| 当前外部系统版本是否匹配 | 实际写入边界 | 防止检查后状态变化造成竞态 |

SHACL 可以表达比表格更多的规则，但表达得出来不代表它一定是最合适的执行位置。例如，把所有用户权限放进离线形状校验，容易忽略会话、撤权和下游动作的变化。把每个简单字段错误交给模型判断，则增加了不必要的不确定性。

<a id="ch05--56-怎样处理验证失败"></a>

### 5.6 怎样处理验证失败

校验失败的数据应保留来源、失败规则、发现时间和处理负责人。不要为了让报告变绿，自动删除有问题的字段或用模型猜值补齐。修改必须可追溯，而且应能区分源数据修复、映射修复和合同变化。

建议将结果至少分为三类：阻止当前流程的错误、需要人工审查的问题、允许继续但要观察的提醒。SHACL 的结果严重性与业务发布门槛之间需要明确映射；工具的一个布尔值不能代替业务风险判断。

对新增形状，先在代表性数据上旁路检查。若新规则导致大量历史数据不符合，应确认是发现了真实问题，还是无意改变了业务含义。之后再制定修复和迁移安排。

形状本身也要做回归：一组应通过的图、一组应失败的图，以及预期失败的节点和属性路径。只验证一份正确数据，无法证明坏数据会被拦截。

<a id="ch06--第-06-章-本体工程与领域建模"></a>

## 第 06 章　本体工程与领域建模

本章目标是把一份初始概念图发展为可以维护的领域模型。高质量本体来自反复解释真实任务、审查反例和管理变更，并不以概念数量或图形复杂度作为主要成绩。

<a id="ch06--61-先选择模型的用途"></a>

### 6.1 先选择模型的用途

同一个工厂可以按设备台账、空间位置、生产流程、成本归属或维修责任建立不同模型。这些视角都可能合理，但它们不一定应被压进同一棵继承树。

例如，“北厂设备”通常表达当前位置或管理范围，“离心泵”表达设备类型，“本周需要检修的设备”表达随时间变化的工作集合。若全部建成固定子类，迁厂、任务变化和类型知识容易混在一起。

Noy 与 McGuinness 强调，本体设计存在多种可行选择，应由应用目的、预期扩展和迭代反馈决定。[R38](#references--r38) 因此，评审首先要看能力问题，再看类和关系是否支持这些问题。

<a id="ch06--62-类实例属性事件怎样区分"></a>

### 6.2 类、实例、属性、事件怎样区分

`CentrifugalPump` 可以是类，`P-101` 是具体设备实例，序列号和额定功率通常是属性。一次温度观测或一次维修则适合成为事件性对象，因为它们有自己的时间、参与者、来源和结果。

产品型号是一个典型的选择题。如果系统只按型号分类查询，把型号表示成某种类型可能足够。如果型号还关联供应商、设计版本、适用配件和手册，它更适合成为具有独立身份的型号对象，再由实物设备关联它。两种建法都需要解释各自服务的问题。

| 需要表达的内容 | 常用选择 | 应追问的问题 |
| --- | --- | --- |
| 相对稳定的对象类别 | 类与子类 | 每个实例是否真的都属于上位类 |
| 有长期身份的对象 | 实例 | 它在更名或迁移后是否仍是同一对象 |
| 简单、单值或多值特征 | 属性 | 是否需要单位、有效时间或来源 |
| 带时间和参与者的发生过程 | 事件 / 观测对象 | 是否需要区分发生、记录和确认时间 |
| 随上下文变化的职责 | 角色或有时间的关系 | 谁在何时承担什么责任 |
| 供检索使用的主题词 | 受控词汇或概念体系 | 它表达主题相关，还是严格的实例归属 |

不要因为一个中文词是名词就必然建立实体，也不要因为它是动词就必然建立简单关系。“批准”可能需要批准人、时限、对象快照和撤销状态，因而值得成为记录对象。

<a id="ch06--63-避免把源系统结构当成领域含义"></a>

### 6.3 避免把源系统结构当成领域含义

ERP 的 `equipment_master`、维修系统的 `machine` 和传感系统的 `device` 可能都描述设备，也可能在边界上不同。先确定它们的实体含义、标识范围及生命周期，再决定是否映射到一个领域对象。

如果它们确实是同一台设备，通常应保留一个稳定领域身份，并记录各源系统 ID。若一个系统描述设备型号，另一个描述实物，不应因为名称相似就合并。

同样，不要把所有源列原封不动搬进本体。原始代码、业务状态、展示名称和导入标记需要不同处理。可以在落地层保留原始字段，在领域层公开有定义、可维护的属性。一个新读者应能理解 `operatingStatus` 的含义、权威来源和允许值，而不必追查某张历史表的缩写。

<a id="ch06--64-复用标准词汇但先检查含义"></a>

### 6.4 复用标准词汇，但先检查含义

复用现有词汇能够减少重复定义，也便于交换数据。PROV-O 描述来源与生成过程，OWL-Time 描述时间概念，SOSA/SSN 描述传感、观测及相关对象。[R14](#references--r14) [R15](#references--r15) [R16](#references--r16)

复用不是简单复制前缀。需要检查类和属性原本的含义、约束、版本及预期推理。例如，观测的“结果时间”与设备台账“最后修改时间”并不相同；直接复用一个时间属性可能掩盖数据含义的差异。

本教程先采用小型自定义 `ex:` 模型，以便读者看清工程机制。它没有宣称实现完整 SOSA/SSN，也没有把自定义温度记录自动等同于行业测量标准。实际项目可以为必要部分建立明确映射，并用能力问题检查映射是否保留了业务语义。

<a id="ch06--65-skos-与-owl-的边界"></a>

### 6.5 SKOS 与 OWL 的边界

SKOS 适合组织主题词、概念方案、首选名称、替代名称和概念间映射。知识检索需要“轴承异常”“轴承故障”等词汇关系时，它可能比不断增加 OWL 类更合适。[R13](#references--r13)

`skos:broader` 表示概念体系中的直接或常规上位关系，不能直接当作 `rdfs:subClassOf` 使用。SKOS 另外提供 `broaderTransitive` 等关系；不同属性具有不同语义。术语之间有上位关系，不代表某个对象的类型会按 OWL 类继承自动传播。

映射同样分层。两个目录中的概念高度对应，可以考虑合适的 SKOS 映射关系；两条记录确实指向同一个实物，才进一步考虑实体同一性。`owl:sameAs` 的语义远强于“名字类似”或“主题相关”。

<a id="ch06--66-建立可审查的本体工作方式"></a>

### 6.6 建立可审查的本体工作方式

一次本体变更至少留下：变更理由、受影响能力问题、示例数据、旧行为、新行为和迁移方式。新增类通常比改变现有类的含义更容易兼容，但新增公理也可能改变推理结果，所以不能只按文件行数判断影响。

建议在评审时同时打开四份材料：概念图、可执行 RDF/OWL、正反数据样本、能力问题检查。图形帮助讨论，机器可读文件定义执行含义，样本暴露边界，问题检查决定是否有用。

可以使用 Protégé 等编辑器维护和观察模型，也可以采用文本文件与代码审查。[R37](#references--r37) 编辑器能降低操作门槛，但不会替团队决定实体边界。图画得漂亮、推理器没有报错和业务模型适用，是三个不同判断。

<a id="ch07--第-07-章-数据集成时间与来源"></a>

## 第 07 章　数据集成、时间与来源

本章目标是让图中的事实具有可解释的来源、单位、时间和版本。形式正确的三元组可以来自错误映射；AI 系统能否可信，很大程度上取决于这些进入图之前的决定。

<a id="ch07--71-为每类事实确定权威来源"></a>

### 7.1 为每类事实确定权威来源

设备是否退役由哪个系统确认，最新温度来自哪个数据流，适用程序由哪个部门维护，应分别说明。一个系统可以是设备状态的权威来源，却不是实际温度的权威来源。

当两个系统冲突时，不要默认采用最后到达的数据。可以按事实类别确定优先来源，也可以保留两条带来源和时间的主张，交由规则或人工解决。模型不应因为其中一段文字更流畅就选择它作为事实。

数据合同通常包括：实体主键、来源 ID、字段含义、单位、时区、允许值、缺失语义、更新机制、删除行为、质量门槛和负责人。本教程的 CSV 虽然很小，也会拒绝重复业务主键、未知枚举和未定义温标。

<a id="ch07--72-映射是有版本的程序"></a>

### 7.2 映射是有版本的程序

“把数据库转成 RDF”不是纯格式转换。`status=1` 究竟映射为运行中、已启用还是待审核，需要业务解释。`updated_at` 表示内容变更时间还是数据确认时间，也必须先明确。

R2RML 为关系数据到 RDF 的映射提供标准化语言，但它不会替项目决定这些业务口径。[R17](#references--r17) 对 CSV、事件流或复杂 API，也可以使用程序化映射，并明确它采用的是哪种格式和规则。

本教程的导入器是自定义 Python 映射程序，未实现 R2RML。它根据租户和稳定编号生成 IRI，保留类型、区域和版本，将华氏度标准化为摄氏度，并把观测建成独立对象。这个范围应写在文档里，避免把一个小型转换器包装成通用数据集成平台。

映射回归至少要检查：同一输入重跑是否得到同样的业务对象，重复记录是否被识别，缺少设备的观测是否被拒绝，源系统新增枚举是否会被悄悄误解。

<a id="ch07--73-时间至少有几个不同含义"></a>

### 7.3 时间至少有几个不同含义

| 时间 | 含义 | 示例 |
| --- | --- | --- |
| 事件 / 观测时间 | 事情何时发生或被测量 | 09:00 的温度读数 |
| 业务生效时间 | 某个状态或规则从何时生效 | 新程序从 9 月 1 日起适用 |
| 源内容变更时间 | 源记录最后一次改变内容的时间 | 昨天修改了设备名称 |
| 事实确认时间 | 何时确认某状态仍为当前事实 | 09:00 查询确认设备仍处于启用状态 |
| 系统记录时间 | 数据何时进入本系统 | 09:00:08 导入成功 |

这些时间可以相同，也可以不同。若把昨天的名称变更时间当作设备状态的新鲜度依据，即使刚刚成功查询，也可能误报数据过期。反过来，今天重新导入一条旧观测，也不会让观测本身变新。

本教程对设备使用 `asOf` 表示事实确认时点，对温度使用 `observedAt` 表示观测时点，固定业务时钟为 `2026-09-01T09:02:00Z`。动作检查的是事实是否足够新，而不是脚本刚刚运行了多久。

OWL-Time 提供时间点、区间和关系的词汇，但时间存储、历史查询、冲突消解和版本保留仍需由应用实现。[R15](#references--r15)

<a id="ch07--74-用来源记录支持追溯"></a>

### 7.4 用来源记录支持追溯

PROV-O 用实体、活动和代理等概念表达来源关系。[R14](#references--r14) 例如，一份源 CSV 是实体，一次导入是活动，导入程序是软件代理，生成的数据集又是实体。

```turtle
@prefix ex: <https://example.org/maintenance/> .
@prefix prov: <http://www.w3.org/ns/prov#> .

ex:SourceFile a prov:Entity .
ex:ImportRun a prov:Activity ; prov:used ex:SourceFile ;
    prov:wasAssociatedWith ex:Importer .
ex:Importer a prov:SoftwareAgent .
ex:Snapshot a prov:Entity ; prov:wasGeneratedBy ex:ImportRun ;
    prov:wasDerivedFrom ex:SourceFile .
```

这类记录帮助回答“这个值怎么来的”，但不会自动证明来源诚实或内容正确。文件哈希用于识别文件是否相同，签名、访问审计和业务对账承担其他职责，不能把它们混成一个“可信分数”。

本教程实际输出源文件 SHA-256 与导入说明，便于复现。上面的 PROV-O 片段展示更丰富的扩展方式，不能据此声称导入器已经实现完整的来源管理系统。

<a id="ch07--75-更新删除和派生事实失效"></a>

### 7.5 更新、删除和派生事实失效

假设一个类层级变化，或者设备不再属于某条产线。只删除原始边，可能仍然留下以前物化的派生边。系统需要清楚区分显式事实和推导事实，并决定何时重算、如何追踪依赖、怎样删除不再成立的结果。

小型系统可以按完整快照重新构造派生图；大型系统可能需要增量维护、分区和更细的依赖记录。两种方案都应通过“新增、修改、删除、乱序、重复”测试，而不只检查首次导入。

删除还有业务含义。设备退役通常是状态变化，不等于抹掉所有历史观测。文档撤权或删除则可能要求检索索引、缓存、摘要和引用入口同步调整。保留历史与限制继续使用，可以同时成立。

<a id="ch07--76-给模型的是有边界的证据包"></a>

### 7.6 给模型的是有边界的证据包

模型上下文宜包含必要事实、对象版本、单位、时间、来源标识和适用程序，而不是把所有原始表拼成一大段文本。这个证据包应当已经完成权限过滤和必要的质量检查。

例如，设备温度 92 度应连同“摄氏度、观测时间、当前设备身份、来源 ID”一起出现。若最新观测缺失，证据包中应保留缺失状态，让模型输出需要补充的信息。用零填充会把“未知”改成“已知且很低”，进而改变建议与业务动作。

<a id="ch08--第-08-章-sparql存储与查询"></a>

## 第 08 章　SPARQL、存储与查询

本章目标是让本体和知识图谱真正服务于查询，同时明确存储产品、查询语义、推理设置和访问控制之间的边界。

<a id="ch08--81-从图模式匹配开始"></a>

### 8.1 从图模式匹配开始

SPARQL 使用图模式描述要匹配的事实。下面的查询寻找设备标识、区域和版本；配套数据图中已经包含类型与子类声明。

```sparql
PREFIX ex: <https://example.org/maintenance/>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?asset ?assetId ?region ?version
WHERE {
  ?asset rdf:type/rdfs:subClassOf* ex:Asset ;
         ex:assetId ?assetId ;
         ex:region ?region ;
         ex:version ?version .
}
ORDER BY ?assetId
```

属性路径中的 `/` 表示路径连接，`*` 表示零次或多次。这里显式沿类型和子类关系查询，不等于启用了完整 OWL 推理。其他公理或由不同规则得到的类型，仍要看具体图与推理配置。[R09](#references--r09)

使用 `SELECT` 获取变量绑定，`ASK` 判断图模式是否存在，`CONSTRUCT` 构造结果图。修改数据则属于 SPARQL Update 等写入接口，应与普通只读查询分别授权。[R10](#references--r10)

<a id="ch08--82-结果数量可能不是对象数量"></a>

### 8.2 结果数量可能不是对象数量

RDF 图按集合保存三元组，但 SPARQL 查询结果可能具有重复解的多重集语义。一个设备有两种语言标签、三个观测时点，连接查询可能产生多行。若直接 `COUNT(*)`，可能把组合结果误当成设备数。[R09](#references--r09)

要统计设备，可以根据问题使用 `COUNT(DISTINCT ?asset)`；要取得最新观测，则必须明确时间排序、相同时点冲突以及是否允许无观测。随意加 `DISTINCT` 虽能减少重复行，却不能修复错误的业务连接。

`OPTIONAL` 同样需要理解。把某个过滤条件放在可选模式内部或外部，可能改变缺少值的记录是否被保留。应为“没有观测的设备”准备一条测试，确认查询没有悄悄把它从需要处理的对象中排除。

<a id="ch08--83-查询中的不存在具有范围"></a>

### 8.3 查询中的不存在具有范围

`FILTER NOT EXISTS` 可以表达在当前查询数据和模式下没有匹配结果。它不自动证明现实世界不存在相应事实。

例如，“没有维修记录的设备”可能仅表示当前获准查询的数据集中没有记录。若用户无权看历史维修图，结果甚至会受到权限范围影响。面向业务人员展示时，应说明数据覆盖和时间范围，不能直接写成“这些设备从未维修”。

这也是开放世界语义与应用查询可以共存的方式：应用可以基于有限数据计算结果，但需要准确解释结果代表什么。

<a id="ch08--84-模型调用业务查询而不是任意端点"></a>

### 8.4 模型调用业务查询，而不是任意端点

在本教程中，面向模型的能力是 `context(principal, asset_id)`。服务从可信身份确定租户和区域，再用固定查询及参数绑定获取观测。模型不提供自己的角色，也不自由选择命名图或远程端点。

RDFLib 支持参数绑定，这有助于将值与查询文本分开。[R18](#references--r18) 但仅做字符串转义还不够：任意 SPARQL 可以包含远程 `SERVICE`，任意解析输入也可能引入外部访问。还需要固定查询模板、资源预算、输出限制和运行环境控制。[R39](#references--r39)

高级分析用户可能确实需要自由查询。此时应建立独立的分析环境、访问规则、审计和超时机制，不应把普通智能体工具的权限一起放宽。

<a id="ch08--85-存储路线怎样选择"></a>

### 8.5 存储路线怎样选择

| 路线 | 常见优势 | 需要承担的工作 |
| --- | --- | --- |
| 关系数据库与业务服务 | 事务、约束、现有系统集成成熟 | 显式维护语义映射、关系查询和业务接口 |
| RDF 存储与 SPARQL | RDF 数据交换、图模式与相关语义生态 | 配置推理、索引、事务、访问和运维 |
| 属性图数据库 | 对带属性的节点和关系进行直接建模与遍历 | 明确与 RDF/OWL 概念的映射和差异 |
| 内存 RDFLib | 小型实验、文件处理、原型容易复现 | 容量、并发、持久化和生产治理需另外设计 |
| 统一数据与业务平台 | 共享对象、应用、治理与交付能力 | 采购、平台能力边界、适配与退出迁移 |

属性图和 RDF 都可以表达关系，但数据模型、标识、语言标签、多值、关系属性和推理机制不完全相同。Neo4j 文档对属性图中的节点、关系和属性有明确说明；不能因为画面都是节点与边，就把它当成开箱即用的 OWL 推理器。[R23](#references--r23)

Jena Fuseki 提供 SPARQL 服务能力，GraphDB 提供相应的存储与推理配置。这些是候选工具的功能定位，不是本书对它们在你的负载下作出的性能排名。[R22](#references--r22) [R24](#references--r24)

<a id="ch08--86-性能问题先还原工作负载"></a>

### 8.6 性能问题先还原工作负载

需要估计的内容包括：显式和派生三元组数量、更新频率、关系分布、常用查询、权限过滤方式、并发和响应目标。平均关系数量很小，但个别节点连接大量对象，可能使某些扩展路径非常昂贵。

对模型工具尤其要限制邻域扩展：允许哪些谓语，最大深度是多少，最多返回多少对象，何时截断并说明结果不完整。本教程沿固定 `partOf` 路径进行有限扩展，每一步都检查范围；它没有向模型开放无限图遍历。

基准测试应包括冷启动、缓存命中、增量更新、推理重算、权限过滤后召回和故障恢复。不要只测一个无过滤、无更新的顺利查询，再把结果用于生产容量承诺。

## 第 09 章　本体辅助的 RAG

本章目标是把本体用于取得正确证据，并准确区分关键词检索、向量检索、关系检索以及不同的 GraphRAG 方法。

<a id="ch09--91-rag-的知识来自哪里"></a>

### 9.1 RAG 的知识来自哪里

Lewis 等人的 RAG 工作将参数化模型与非参数记忆结合，在其具体实验中使用检索索引为生成提供资料。[R27](#references--r27) 今天工程实践中的 RAG 包含许多实现，但核心问题仍然是：面对一个任务，系统怎样取得足够、适用、可访问的外部证据。

检索正确并不能自动保证生成正确。模型可能忽略证据、混淆条件、引用无关段落或添加未被支持的结论。因此应把检索质量、引用支持和回答正确性分别评估。

在设备案例中，需要两类证据：当前温度与设备状态来自结构化查询，适用检查程序来自文档。只把所有内容切成文本块，会丢失一些原本明确的对象关系和时间含义。

<a id="ch09--92-用关系解决措辞未重合的问题"></a>

### 9.2 用关系解决“措辞未重合”的问题

用户输入 `P-101`，但通用程序文档没有列出每台设备编号。关键词检索可能先找到资产目录；向量检索是否能找到程序，取决于表示、文本和查询。若知识层明确记录 `P-101 usesProcedure PROC-PUMP-01`，系统就能沿关系取得适用程序。

关系检索的优势来自已经治理的连接。它的代价也同样明确：关系需要建立、维护和检查。如果设备更换了型号而程序关联没有更新，图检索可能非常稳定地找到错误程序。

因此，本体辅助 RAG 不应只是“多走几条边”。它需要理解关系的方向、有效时间、适用条件和维护责任。

<a id="ch09--93-一条可控的检索链路"></a>

### 9.3 一条可控的检索链路

建议把流程组织为：

1. 从可信会话取得访问范围，解析或确认任务对象。
2. 通过明确查询读取结构化事实、版本和时间。
3. 沿允许的业务关系找到候选知识或文档类别。
4. 在权限和有效期过滤后的范围内进行关键词、向量或其他检索。
5. 按任务需要重排、去重和限制上下文长度。
6. 将事实、文档、来源与缺失信息组成证据包。
7. 生成结构化建议，再验证关键事实和动作参数。

其中的实体定位可以由用户选择、精确标识、别名字典或模型辅助完成。本教程使用显式设备编号，不把自然语言实体消歧算作已实现能力。面对“那台老泵”这样的输入，生产系统应提出澄清，而不是任意选一台。

<a id="ch09--94-向量表示与本体怎样协作"></a>

### 9.4 向量表示与本体怎样协作

向量适合处理措辞变化、同义表达和语义近邻。本体可以提供过滤条件、关系路径、类型信息和证据结构。二者可以组成混合方案：先按业务关系缩小范围，再对候选文档做向量检索；也可以先召回文本，再将其中实体链接回图进行补充核查。

选择顺序取决于任务。明确对象的程序查询，关系路径可能很有效；跨资料寻找相似故障描述，向量检索可能更有价值。无论采用哪种路径，都要检查过滤后的召回，而不是只报告未经权限过滤的理想结果。

不要把相似度当作事实真值。两个故障描述相近，不代表故障原因相同；一个文档片段离查询向量很近，也不证明其中规则对当前设备生效。

<a id="ch09--95-graphrag-不是一个统一实现"></a>

### 9.5 GraphRAG 不是一个统一实现

Microsoft GraphRAG 的官方索引流程包括从文本抽取实体、关系和主张，进行社区检测，生成多层社区摘要，并建立向量表示。[R25](#references--r25) 其原始工作重点之一是针对整个语料集合的全局理解与摘要问题。[R26](#references--r26)

这与“根据已治理的设备关系找到一个程序”是不同的工程场景。前者需要处理抽取误差、社区结构、摘要成本和全局回答评估；后者更关心实体、精确关系、时效和受控应用。两者可以结合，但不能用同一个 GraphRAG 标签掩盖实现差异。

同样，从文本自动得到实体关系图，并不等于已经获得完整 OWL 本体。是否有显式类型、公理、约束、权限和来源，要看实际设计。

<a id="ch09--96-用本教程的结果理解收益边界"></a>

### 9.6 用本教程的结果理解收益边界

配套实验设计了四条检索问题。其中两条仅给出设备编号，两条在文字中有较充分的程序线索。使用相同合成资料和显式设备身份，运行结果为：

| 方法 | 正确首条文档 | 分母 | 说明 |
| --- | ---: | ---: | --- |
| 词项重合基线 | 2 | 4 | 没有向量模型，也不是精调的生产搜索引擎 |
| 词项重合 + 程序关系 | 4 | 4 | 已知设备到适用程序的显式关系 |

这些数字展示了关系如何补足特定检索线索，不能作为“图检索普遍比向量检索更好”的证据。样本是人工设计的，规模很小，也没有测量大模型回答质量。工程项目应增加真实问题、错误关系、模糊名称、过期程序和新设备等案例，再评估收益与维护成本。

<a id="ch09--97-引用拒答和上下文预算"></a>

### 9.7 引用、拒答和上下文预算

每条关键事实应能追溯到对象版本或文档位置。引用 ID 存在只是第一步，还要检查引用是否支持结论。例如，程序说“温度异常时检查冷却回路”，并不支持“冷却回路已经损坏”。

当上下文缺少观测、程序过期或关系冲突时，应返回需要补充的信息。把所有缺失都交给模型补全，会破坏本体和检索层已经建立的边界。

上下文预算也应按任务设计。把整片邻域全部送入模型，可能增加噪声、泄漏风险和成本。优先提供与当前问题相关的事实、必要关系、短证据段落及可查询的来源，保留继续取得证据的受控入口。

<a id="ch10--第-10-章-大模型抽取与实体对齐"></a>

## 第 10 章　大模型抽取与实体对齐

本章目标是把模型的语言能力用于产生可检查的候选信息，而不是把每次生成都直接变成知识库中的权威事实。

<a id="ch10--101-从自由文本到候选陈述"></a>

### 10.1 从自由文本到候选陈述

一份维修记录可能写着：“上午巡检时，北厂循环泵显示 92 度，怀疑冷却不良，建议复核。”至少包含四种不同性质的信息：一个观测、模糊的时间、待确认的解释，以及行动建议。

若模型把它抽成“设备故障原因为冷却不良”，就把怀疑升级为事实。正确的抽取合同应保留陈述类别、确定性、原文依据和待补信息。例如，观测可以进入候选观测对象，怀疑进入待验证假设，建议进入提案；它们不应共享一个含糊的 `fact` 状态。

本体提供允许的概念和关系，模型负责从语言中识别可能的内容。二者协作仍然需要实体匹配、单位处理、来源定位和人工或规则审查。

<a id="ch10--102-先定义输出合同"></a>

### 10.2 先定义输出合同

一个候选抽取结果至少可以包含：实体候选、关系、值、单位、时间原文、规范化时间、来源文档、原文位置、引用片段、陈述类别和缺失信息。

字段应允许表达不知道。例如，没有给出温标时，`unit` 可以为空并进入补信息流程；不能仅凭“通常用摄氏度”就总是补上。无法唯一定位“循环泵”时，应返回候选或澄清请求。

JSON Schema 可以限定类型、必填字段、枚举、数组数量及条件关系。[R32](#references--r32) 它不能单独证明值来自原文，也不能证明一个陈述在业务上为真。结构验证、来源检查和语义检查应分开。

本教程对建议输出规定了设备、温度、程序、证据、候选动作和批准要求。模型不能通过附加 `role=admin` 或 `approved=true` 获得权限，因为这些字段既不属于输出合同，也不会被动作服务信任。

<a id="ch10--103-实体对齐是一项独立任务"></a>

### 10.3 实体对齐是一项独立任务

实体对齐要确定一句话中的对象对应哪个已有实体，或是否需要创建新实体。常见依据包括稳定编号、外部系统 ID、名称、型号、地点和时间，但它们的可靠性不同。

建议采用从强依据到弱依据的顺序：先检查获准范围内的稳定标识；再检查经维护的别名；必要时进行相似度候选检索；最后由规则、领域人员或有边界的模型判断。存在多个合理候选时，应保留歧义。

| 情况 | 合理处理 | 不应直接做的事 |
| --- | --- | --- |
| 同编号、不同租户 | 在可信租户范围内定位 | 全局按编号合并 |
| 同名、不同型号 | 保留多个候选并补充条件 | 选相似度最高者作为确定事实 |
| 设备更名 | 更新名称并保留身份和别名 | 自动创建一台新设备 |
| 两个来源确为同一实物 | 记录映射证据与批准过程 | 仅凭名称接近就使用 sameAs |
| 新出现的型号名称 | 进入受控词汇或建模评审 | 让模型任意扩展核心类体系 |

本教程接收显式设备编号，验证的是身份边界和结构化输出，未实现通用自然语言实体链接器。读者扩展别名匹配时，应加入同名、迁厂、更名和跨租户案例。

<a id="ch10--104-候选知识进入正式图之前"></a>

### 10.4 候选知识进入正式图之前

可以采用三层数据区：原始资料区、候选陈述区和已接受知识区。候选区保存模型版本、提示版本、来源、抽取结果、校验记录和审核状态。未接受的陈述不应被后续问答当成确定事实。

批准进入知识库也不一定意味着永久正确。源文档撤回、设备身份被纠正或事实过期时，需要找到受影响陈述并重新处理。来源关系和版本是支持这种更新的基础。

如果模型建议修改本体本身，例如新增类、改变关系的 domain 或增加等价公理，影响会超过单条记录。此类变更应进入本体评审与回归流程，不能和普通事实抽取共用一个“写入成功”按钮。

<a id="ch10--105-给模型足够明确的上下文"></a>

### 10.5 给模型足够明确的上下文

提示中说明任务、允许概念、输出结构、失败条件和来源使用规则。提供几个正常与异常例子，尤其是“信息不足”“多个候选”和“原文只是猜测”的情况。

不要把模型内部思考过程作为审计资料。可以要求输出简短理由、引用位置、字段来源和缺失项；这些是用户能核查的解释。模型给自己报出的置信度，需要经过独立校准后才可能用于排序，不能直接代替业务门槛。

结构化输出能力有助于减少格式错误。Ollama 官方文档支持通过 `format` 传入 JSON Schema，也建议在提示中提供相应结构；本书查阅时，文档还注明 Ollama Cloud 不支持结构化输出。[R30](#references--r30) 因此教程默认面向本地、自备模型环境，仍在客户端重新校验结果。

<a id="ch10--106-怎样评估抽取"></a>

### 10.6 怎样评估抽取

至少分别检查实体识别、实体对齐、关系正确性、数值单位、时间、来源支持和陈述类别。一个字段完整率很高的系统，仍可能把每条“怀疑”都抽成确定故障。

评估样本应覆盖否定、条件句、修订记录、历史事件、跨页引用和同名实体。近重复文档不能随意分到训练调试集和独立测试集两边，否则结果容易过于乐观。

若输出将影响业务动作，关键字段还应经过服务端检查。例如，本教程把模型报告的温度与授权查询所得值比较，把程序 ID 与设备关系比较，并检查引用是否来自本次证据包。但自由文本摘要中的每一个说法仍需另外评价；这些有限检查不能被报告为完整语义验证。

2. 模型输出符合 JSON Schema，引用 ID 也存在。为什么仍然可能出错？请设计两条反例和相应检查。

<a id="ch11--第-11-章-智能体与业务动作"></a>

## 第 11 章　智能体与业务动作

本章目标是把本体中的对象和动作接入智能体，同时保留可靠的权限、批准、状态与恢复机制。语言输出和业务效果必须有不同的证明方式。

<a id="ch11--111-工具应暴露业务含义"></a>

### 11.1 工具应暴露业务含义

一个工具叫作 `updateRow`，要求模型填写表名、字段和值，难以体现业务前提。`createMaintenanceDraft` 则表达明确意图：为特定设备创建一份维修工单草稿。它应说明允许输入、完成条件和副作用范围。

本体或领域模型提供共用对象与关系，工具合同提供可执行入口。Palantir 的 Action Types 将业务操作与对象修改及相关副作用结合，是一种平台实现。[R34](#references--r34) [R35](#references--r35) 在自建系统中，也可以用业务服务实现同样清楚的边界。

工具不宜让模型直接选择生产数据库表、访问凭据或任意网络地址。读取、计算、保存提案、创建草稿和高影响操作，应按各自风险分别设计。

<a id="ch11--112-建议批准和执行是不同记录"></a>

### 11.2 建议、批准和执行是不同记录

建议说明“可以做什么”，批准记录“谁同意了哪一个具体方案”，执行记录“系统实际尝试了什么”，回执说明“外部系统确认了什么”。把这些合并为一条模型消息，会失去重要状态。

本教程的提案快照包含设备、版本、温度、时间、程序、文档哈希、证据和动作名称。批准绑定快照哈希与有效期。模型不能自行填写一个批准人后让它生效；批准来自可信服务记录。

执行前重新读取当前事实。如果设备版本、程序内容或政策变化，旧批准不能无条件继续使用。即使新方案看起来“差不多”，用户批准的仍然是旧快照，系统需要按规则刷新并重新批准。

<a id="ch11--113-真实写入边界需要再次检查"></a>

### 11.3 真实写入边界需要再次检查

在本体服务里检查设备仍为版本 7，随后去工单系统写入，中间可能已经发生变化。能否避免这类竞态，取决于真正执行写入的系统是否支持条件检查或其他相应机制。

本教程的外部模拟器在自己的数据库事务中核对设备状态和期望版本，再创建草稿。这演示了一种条件写入方式。现实 ERP、工单或设备系统是否具备同样语义，需要逐项确认。

本体内部提交成功、消息发出成功和外部业务提交成功，是不同事件。跨系统没有默认的共同事务；不能仅凭工具框架支持重试，就宣称业务效果恰好发生一次。

<a id="ch11--114-两层去重"></a>

### 11.4 两层去重

第一层是请求幂等：同一租户与幂等键重复提交，应返回原结果或当前状态；同一个键绑定不同提案，应报告冲突。记录必须持久化，多个工作进程需要通过原子方式争取执行权。

第二层是业务唯一性：同一提案只允许建立一条业务执行记录。客户端换一个幂等键，也不能绕过这个约束再创建一份草稿。生产系统若要求“同一异常事件只允许一个有效工单”，还应把事件或业务任务标识纳入相应约束；仅限制提案并不能阻止人为创建两个不同提案。

外部系统同样需要稳定请求标识。只有本地去重、外部重复执行仍不受控，不能解决超时重试后的重复业务效果。

<a id="ch11--115-超时可能意味着结果未知"></a>

### 11.5 超时可能意味着结果未知

外部系统可能已经创建草稿，但响应在网络中丢失。这时把任务记为“失败，马上再创建”会产生重复，把它记为“成功”又缺少证据。

本教程使用 `outcome_unknown`，随后按稳定请求 ID 查询回执。匹配的回执确认后，才进入 `executed`。如果暂时查不到记录，也不一定能证明迟到或并发操作永远不会提交，因此保持未知状态并继续受控处理。

| 状态 | 可以说明什么 | 后续处理 |
| --- | --- | --- |
| awaiting_approval | 提案存在，尚未获准执行 | 展示证据并等待有权人员 |
| executing | 已取得执行权，正在尝试 | 查询同一执行记录，避免再创建 |
| outcome_unknown | 无法确认外部效果 | 对账、查询、必要时人工接管 |
| executed | 已确认匹配的草稿回执 | 展示草稿结果，不宣称完成维修 |
| failed | 已确认被本示例外部系统拒绝或未成功 | 修复原因后按规则生成新提案 |

状态更新也需要并发保护。一条晚到的“未知”结果不能覆盖已经确认的成功回执。教程为这个情形提供了单独的回归检查。

<a id="ch11--116-模型怎样参与多步任务"></a>

### 11.6 模型怎样参与多步任务

可以让模型提出下一步需要什么信息、选择允许的只读工具、比较获准候选，并形成结构化提案。对流程状态、批准、幂等和回执，使用确定性服务维护权威记录。

若任务本身步骤固定，简单状态机往往足够。只有在实际问题需要灵活分解、探索或选择时，再引入更复杂的智能体计划。无论计划来自模型还是人工，真实动作仍通过同一套业务验证。

扩大自治应以证据为条件：先离线回放，再影子比较，然后人工批准，最后只对经过验证的范围考虑自动执行。人工批准要有足够证据和时间，不能只是为了让流程图看起来完整而增加一次点击。

<a id="ch12--第-12-章-神经符号系统设计"></a>

## 第 12 章　神经符号系统设计

本章目标是合理安排模型与符号组件的职责。神经网络擅长从数据中学习模式，符号模型擅长表达明确结构和规则；组合价值需要落实到具体任务和验证方式。

<a id="ch12--121-先说明采用哪种组合"></a>

### 12.1 先说明采用哪种组合

“神经符号”覆盖多种研究和工程路线。本书主要讨论工程组合：模型处理语言与候选生成，知识层提供对象和关系，规则与推理器处理明确语义，服务验证执行条件。它不宣称这个组合已经实现了联合训练的神经符号学习算法。

Pan 等人的路线综述把 LLM 与知识图谱结合分成图谱增强模型、模型增强图谱，以及二者协同等方向。[R29](#references--r29) 这有助于区分研究目的，但具体系统仍要说明输入、输出和事实责任在哪里。

例如，图谱辅助检索使用知识帮助模型回答；模型抽取候选关系使用语言能力帮助构图；模型提出计划、符号模块校验计划，则是另一种协作方式。不能因为都使用了图和模型，就将它们的效果互相替代。

<a id="ch12--122-区分四种得到结论"></a>

### 12.2 区分四种“得到结论”

| 方式 | 结论的依据 | 如何验收 |
| --- | --- | --- |
| 逻辑蕴含 | 公理、事实和指定语义 | 检查前提、推理范围与预期结论 |
| 规则计算 | 有版本的业务规则 | 检查边界值、优先级与例外 |
| 统计预测 | 数据分布和训练得到的模型 | 用独立样本评价误差、校准和漂移 |
| 语言生成 | 上下文与模型的生成过程 | 检查事实、引用、任务完成和不确定性 |

设备属于厂区可以来自关系传递；温度超过阈值来自数值规则；未来七天故障概率来自预测模型；给操作员解释步骤则可能来自语言模型。把四者都叫作“推理”，容易丢失结论强度和验收方式。

尤其要区分蕴含与图补全。链接预测模型给某条边很高分，说明它在模型下很可能成立，不等于这条边由现有公理必然推出。高分候选仍需来源、规则或人工审核，才能进入相应的权威知识层。

<a id="ch12--123-一种稳健的职责分工"></a>

### 12.3 一种稳健的职责分工

对于设备案例，可以采用：模型识别用户意图与需要的证据；领域查询定位设备；规则标准化单位并检查时间；OWL RL 推导指定类型与关系；检索器取得程序；模型组织建议；服务校验关键参数并管理批准和回执。

这种分工不是为了最大化组件数量，而是让每一步拥有清楚的责任。如果某一步可以用简单确定性逻辑完成，就应把模型是否带来额外收益作为单独问题。

例如，计算华氏度到摄氏度的转换，不需要模型发挥创造性。判断一份自由文本是否只是表达怀疑，则可能需要语言处理和领域审查。把计算交给程序、把语言候选交给模型，会更容易定位错误来源。

<a id="ch12--124-约束规划与语言计划"></a>

### 12.4 约束规划与语言计划

一个计划可以表示为动作序列，每个动作具有前置条件与预期效果。模型可以提出候选序列，符号检查器验证动作是否允许、依赖是否满足、资源是否冲突。

但“计划在模拟状态上成立”仍不保证现实执行成功。传感数据可能延迟，外部系统可能拒绝，资源也可能被其他任务占用。因此计划执行要有观察、状态更新、失败分支和必要的重新规划。

如果涉及排班、路线或资源分配，可以考虑优化求解器、约束规划或业务规则引擎。它们与本体的关系是共享对象和约束，而不是由本体自动代替求解算法。求解目标、可行域和近似策略必须另外定义。

<a id="ch12--125-让不同类型的解释各归其位"></a>

### 12.5 让不同类型的解释各归其位

逻辑解释可以说明使用了哪些公理和事实；预测解释可能说明重要特征或统计关联；业务解释说明为什么按当前制度采用某项动作；语言模型的文字说明则是供人理解的呈现。

这些解释不能随意混用。例如，模型能写出一条合理理由，不代表它具有形式证明。特征重要性也不直接构成因果证据。对外说明时，应标清依据类型，并给出可以检查的来源与限制。

本教程的 OWL-RL 部分检查具体蕴含，但没有实现证明树展示。动作部分则有明确状态与回执，可以证明草稿是否被模拟系统确认。它们分别提供不同层面的可解释性。

<a id="ch12--126-怎样判断组合是否值得"></a>

### 12.6 怎样判断组合是否值得

先做消融比较：移除关系检索会怎样，移除规则检查会怎样，仅保留简单模板是否已经足够。观察任务正确性、失败代价、维护工作量和运行成本，而不只看模型回答是否显得聪明。

同时计算知识维护成本。模型版本升级需要回归，本体变更也需要回归；关系来源、规则负责人和弃用流程如果不清楚，组合系统可能比简单方案更难维护。

设计成功的标志，是团队能够解释某个错误发生在哪一层、如何修复，以及修复后哪些旧结论和动作需要重新检查。

2. 一个固定三步的业务流程全部交给多智能体协商。你会怎样设计比较实验，判断这种复杂度是否有必要？

<a id="ch13--第-13-章-安全与治理"></a>

## 第 13 章　安全与治理

本章目标是保护从原始数据、派生知识到模型输出和实际动作的完整路径。本体可以表达权限相关概念，真正的限制仍必须在访问和执行位置生效。

<a id="ch13--131-可信身份先于模型上下文"></a>

### 13.1 可信身份先于模型上下文

租户、用户、角色和区域应来自身份系统与服务端会话。模型输出里的 `tenant` 或“用户已经同意”，都不能成为授予权限的依据。

本教程用固定 `Principal` 对象代表可信身份，方便测试不同角色。它展示服务层检查方式，没有实现生产登录、目录同步、多因素验证或数据库文件隔离。能直接读取本地样本文件的开发者当然可以看到全部合成数据；不能把教学项目的文件布局误认为多租户安全产品。

真实系统应确保模型只能通过受控服务获得上下文，普通使用者不能绕过服务直接读取所有图、索引或业务数据库。

<a id="ch13--132-命名图检索索引和缓存都需要边界"></a>

### 13.2 命名图、检索索引和缓存都需要边界

按租户分图有助于组织数据，但查询接口仍需限制可访问图。区域、项目或记录级规则也可能比租户更细。本教程首先选择租户图，再检查设备区域，沿关系扩展时继续检查每个目标节点。

文档检索应在内容进入模型之前完成权限与有效期过滤。向量索引、关键词索引和图关系都不能成为越权获取资料的旁路。

缓存键也需要包含会影响结果的身份或访问范围、数据版本和策略条件。如果只按自然语言问题缓存答案，不同权限用户可能收到相同的高权限摘要。删除、撤权和版本变化应触发相应的失效机制。

<a id="ch13--133-派生内容不会自动继承所有保护"></a>

### 13.3 派生内容不会自动继承所有保护

一个用户有权读取某组数据，不表示他生成的摘要可以分享给任何人。推理结果、模型回答、导出文件、日志和下游应用都可能包含派生的敏感信息。

Palantir 的访问控制传播文档明确区分不同控制及下游传播边界；部分读取时过滤的控制不会自动附着到所有派生或外部输出上。[R36](#references--r36) 自建系统同样应逐条检查数据离开原访问层之后的用途。

推理也可能扩大可见信息。两个单独看来普通的关系连接起来，可能暴露敏感关联。是否允许某种派生结果，需要根据业务分类和接收方决定，而不是仅看原始三元组能否分别读取。

<a id="ch13--134-防止资料变成指令"></a>

### 13.4 防止资料变成指令

检索文档可能包含“忽略规则”“导出所有租户记录”等恶意文本。这些内容应作为待分析资料，而不是改变系统角色、工具范围或授权的命令。

提示中的说明有帮助，但关键控制应独立于模型：工具只接受限定参数，权限检查使用可信身份，高影响动作需要批准，模型没有任意读取文件、访问网络或执行代码的入口。

本教程的恶意文档测试验证的是这些确定性边界：文档不能改变固定身份，模型额外权限字段会被拒绝，只读身份不能执行动作。它没有运行真实模型红队评估，因此不能据此宣称某个模型对提示注入“免疫”。

<a id="ch13--135-rdf-解析和查询也可能访问外部资源"></a>

### 13.5 RDF 解析和查询也可能访问外部资源

RDFLib 文档提醒，JSON-LD 的远程上下文及 SPARQL 联邦查询等能力可能访问网络或文件。[R39](#references--r39) 这意味着“只是读一个知识文件”不一定永远是纯本地操作。

处理不可信输入时，应限制允许格式、来源、大小、解析资源和网络出口。对于必须访问外部词汇的系统，可以采用受控镜像、允许列表及明确版本。仅在应用代码中检查一个字符串前缀，通常不足以覆盖所有间接访问路径。

本教程只解析受控本地文件，并使用固定查询。可选模型接口的地址由操作者配置，不能由文档或模型结果决定；默认只允许回环地址，远程地址需显式选择。

<a id="ch13--136-保护动作与运行记录"></a>

### 13.6 保护动作与运行记录

执行权限需要在首次写入前重新检查，批准绑定具体快照。对账和读取旧回执也需要对象范围校验，不能因为请求曾经执行过就向任何人返回结果。

本地执行记录和外部回执之间要核对请求 ID、对象、载荷哈希和状态。收到不匹配回执时，应保持待确认，不能展示成成功。已确认成功也不能被较晚到达的未知结果覆盖。

日志保留足够的版本、来源和状态来排障，但不默认保存全部原文、凭据或模型内部思考。访问日志本身也需要权限、保留期和清理责任。对业务副作用的恢复应通过合法的补偿或修复动作完成，应用回退不会自动撤销已经生效的操作。

### 思考题

2. 一个 SPARQL 代理承诺“只读”，但允许任意 `SERVICE` 地址。它仍然可能带来哪些访问和资源风险？

<a id="ch14"></a>

<a id="ch14--第-14-章-评估与可观测性"></a>

## 第 14 章　评估与可观测性

本章目标是回答两个问题：增加本体究竟改善了什么；系统答错或执行失败时，怎样找到原因。评估对象应是完整任务和明确组件，不能只统计回答是否流畅。

<a id="ch14--141-先写出要证明的主张"></a>

### 14.1 先写出要证明的主张

“本体提高 AI 质量”太宽泛。可验证的主张可以是：“对于明确给出设备编号、需要找到适用维修程序的任务，增加经过维护的设备—程序关系，提高首条结果命中率，同时不增加越权内容。”这个主张限定了输入、任务、机制、指标和代价。

一个项目通常需要多层指标：

| 层次 | 要检查的内容 | 典型指标或证据 |
| --- | --- | --- |
| 数据与语义 | 标识、映射、单位、约束、推理范围 | 重复身份数、形状违反率、能力问题通过率 |
| 检索 | 是否取得正确且获准的证据 | Hit@k、Recall@k、过期证据率、越权结果数 |
| 生成 | 陈述是否得到证据支持 | 关键字段正确率、引用支持率、合理拒答率 |
| 动作 | 是否正确授权、执行、恢复 | 重复业务效果数、错误执行数、未知结果持续时间 |
| 业务 | 是否改善实际工作 | 每项任务人工时间、完成率、返工、总成本 |

不同层次不能互相代替。检索命中不代表生成正确，草稿创建不代表维修成功，操作耗时缩短也可能伴随质量下降。

<a id="ch14--142-建立可比较的基线"></a>

### 14.2 建立可比较的基线

比较前固定数据快照、访问身份、任务、候选文档和结果预算。先建立能正常工作的简单方案，再逐步增加关系、推理、重排或模型。这样才能判断收益来自哪里。

本教程比较词项重合检索和增加 `usesProcedure` 关系的检索。两者都收到明确资产编号，使用相同权限与有效期过滤；图模式另外把程序关联作为排序依据。它没有比较向量模型，也没有评估从自然语言定位设备的能力。

四条人工设计案例中，词项基线 Hit@1 为 2/4，图模式为 4/4。计算方式是“首条结果包含指定目标文档的案例数 ÷ 检索案例数”。这组数据刻意包含“编号出现在资产目录，但维修程序正文不含编号”的情况，因此适合解释机制，不能代表真实问题分布。

<a id="ch14--143-做消融而不只是比较两个大系统"></a>

### 14.3 做消融，而不只是比较两个大系统

假设完整方案同时加入图关系、重新切分文档、更强模型和更长上下文，最终提高了表现。仅凭总分无法归因于本体。

可以设计以下实验组：相同检索基线；基线加关系；再加受控推理；再加重排；最后比较生成器。每次尽量只改变一个因素，并报告延迟和维护成本。若对系统做多轮调参，最后应在未参与调参的样本上评估。

本体关系也会出错，应单独分层统计关系完整、关系缺失、关系过期、关系冲突和跨权限边界的任务。一个仅在关系完美时有效的方案，仍需要明确上线的数据条件。

<a id="ch14--144-评估集应包含失败路径"></a>

### 14.4 评估集应包含失败路径

正常样本检查有用性，反例检查边界。设备案例至少需要以下变化：同名跨租户、区域不匹配、观测缺失、时间过期、单位未知、多个同刻观测、引用不存在、程序已失效、批准后版本变化、执行响应丢失。

问题文本不同但源自同一文档或同一设备事件的样本，不宜随机散落在调试集与测试集中。可按设备、客户、来源文档或时间划分，并保留变化记录。不能把“40 个测试通过”解读成“40 个真实客户任务成功”：单元和集成测试主要验证已知行为契约。

生成结果应由可操作的判定规则评价。例如，“温度数值与授权观测一致”“引用片段确实支持该建议”“没有将怀疑说成确诊”。需要领域判断时，可由两位审核者独立评分并处理分歧。模型裁判能辅助扩展规模，但仍要用人工校准，并检查它是否偏好更长或更像参考答案的文本。

<a id="ch14--145-记录足以定位问题的链路"></a>

### 14.5 记录足以定位问题的链路

每次任务使用关联 ID，连接输入范围、数据快照、查询模板、检索文档版本、模型及提示版本、校验结果、提案、批准、执行请求与回执。日志保留必要标识和简短原因，原文与凭据按权限和保留期单独处理。

推荐把失败归到可负责修复的层次：身份定位失败交给身份与映射负责人；数据过期交给数据链路；正确文档未召回交给检索；有证据却说错交给生成与校验；批准后写入失败交给动作服务。只保存最终聊天文本，很难做这种诊断。

业务时钟与运行时间应分开。本教程固定业务时钟为 `2026-09-01T09:02:00Z`，方便复现新鲜度检查；评估报告的 `executed_at` 记录实际运行时间。固定时钟不是生产系统停用过期控制的理由。

<a id="ch14--146-把上线门槛写成可执行决策"></a>

### 14.6 把上线门槛写成可执行决策

门槛由任务后果决定。只读摘要可以容许用户纠正，创建业务记录则需要更严格的授权、去重和恢复要求。不要把严重错误平均进一个漂亮的总分。

例如，试点可以要求：所有已定义越权反例均被拒绝；所有未知结果都能查询并交给责任人；关键字段必须通过独立校验；业务效果达到约定目标后才扩展范围。数值门槛应由真实基线和业务风险制定，本书不提供冒充行业标准的统一百分比。

扩展评价时，同时记录本体维护工时、源数据修复工时、模型成本、存储与运行成本。净收益可按“节约的人工与避免的损失，减去建设、维护和运行成本”估算，假设和不确定性应随结果公开。

配套操作见[第 09 课](#lesson09)与[实测记录](../../tutorials/ontology-ai/reports/verification.md)。

2. 系统总体任务成功率很高，但偶尔重复创建工单。为什么不能只按平均成功率决定上线？应增加什么指标和门槛？

## 第 15 章　平台、工具与选型

本章目标是把工具放回系统职责中。不同工具处理建模、存储、逻辑、校验、检索或业务操作，名称中都出现“图”或“本体”并不意味着可以直接互换。

<a id="ch15--151-先判断需要哪种语义能力"></a>

### 15.1 先判断需要哪种语义能力

如果需求是统一字段解释与少量关联查询，关系数据库加数据字典也可能足够。如果需要共享词汇、跨来源身份、可交换图数据和明确逻辑语义，RDF 与 OWL 工具链更有吸引力。如果团队主要进行关系遍历、图算法与应用开发，属性图可能更适合现有技能。

若目标还包括业务对象应用、受控动作和平台治理，就应评估完整业务平台。采购一个图数据库，并不会自动获得组织流程、权限传播、用户界面或动作恢复。

<a id="ch15--152-核心工具的职责"></a>

### 15.2 核心工具的职责

| 工具 | 主要职责 | 适合本书中的工作 | 需要单独核对的边界 |
| --- | --- | --- | --- |
| Protégé | OWL 本体编辑、浏览与扩展 | 类层级、公理、命名与人工评审 | 推理器插件、协作方式、版本管理；不是业务执行平台 |
| RDFLib | Python 中解析、构造、查询 RDF | 小规模原型、导入、教学、嵌入式处理 | 存储插件与数据规模；Python 库不等于托管数据库 |
| OWL-RL | 基于规则扩展图 | 受限推理与机制实验 | 不等于完整 OWL 2 DL 推理和证明服务 |
| pySHACL | SHACL 校验 | 数据合同、候选图质量检查 | 显式指定推理与高级功能；检查复杂度受形状影响 |
| Apache Jena / Fuseki | Java RDF 工具链与 SPARQL 服务 | 服务化查询、规则推理及存储集成 | 各推理配置的覆盖范围、部署与权限安排 |
| GraphDB | RDF 数据库及规则推理 | 需要数据库级 RDF 工作流的项目 | 规则集、版本、许可、集群与运维选项 |
| Neo4j | 属性图存储与查询 | 面向关系遍历的应用与图分析 | RDF/OWL 语义需额外建模或组件，不能从存储结构自动获得 |

这些定位依据相应项目文档，不是性能排名。[R18](#references--r18) [R19](#references--r19) [R20](#references--r20) [R21](#references--r21) [R22](#references--r22) [R23](#references--r23) [R24](#references--r24) [R37](#references--r37)

本书运行锁定 OWL-RL 7.1.4，但本次读取的文档页面标题仍显示 5.2.2；因此具体行为以锁定环境和测试为准。GraphDB 阅读范围为 11.0 文档，也不应自动外推到其他版本。

<a id="ch15--153-palantir-ontology-的工程含义"></a>

### 15.3 Palantir Ontology 的工程含义

Palantir 把 Ontology 定位为连接数据、业务对象及其操作的平台层。对象类型、属性、链接类型和动作类型把数据映射为业务可使用的概念与交互。[R33](#references--r33) [R34](#references--r34) Action Types 描述对对象、属性或链接等执行变更的操作。[R35](#references--r35)

它与本书 RDF/OWL 路线共享“显式业务概念”的思想，但不能因此推定 Foundry Ontology 就是 OWL 文件、默认执行 OWL 蕴含，或所有能力都能通过 RDF 导出保留。平台对象模型、操作模型和 W3C 标准逻辑语义需要分别对照。

设备案例可作如下映射，具体配置应在客户租户与许可范围内验证：

| 本书概念 | 在 Foundry 中需要设计的内容 |
| --- | --- |
| 设备与观测 | 对象类型、属性、主键、源数据映射及更新规则 |
| 设备—产线—厂区 | 链接类型、业务基数、可访问范围 |
| 维修程序 | 文档或相应对象、版本、适用范围及有效期 |
| 创建维修草稿 | 动作类型、参数、提交条件、权限和具体变更 |
| 外部工单系统 | 接口集成、请求标识、回执、幂等与对账责任 |
| 模型建议 | 受控上下文、输出合同、评估及人工审核界面 |

平台内动作成功与外部系统写入成功之间，仍要建立明确的完成定义。访问控制传播也有具体边界，尤其要检查读时过滤、派生输出和外部应用的处理。[R36](#references--r36) 本教程没有连接 Foundry，表格是设计映射，不是已完成平台部署的报告。

<a id="ch15--154-graphrag-与本体编辑器解决不同问题"></a>

### 15.4 GraphRAG 与本体编辑器解决不同问题

Microsoft GraphRAG 的索引流程包含从文本构造图以及生成相关摘要等步骤；其研究讨论了面向语料整体问题的图辅助查询与摘要路线。[R25](#references--r25) [R26](#references--r26) 这与设备维修中“沿已维护程序关系读取特定文档”的任务不同。

文本抽取图常带有不确定的实体、关系和社区摘要。业务本体则需要明确身份、概念及责任。可以把抽取图作为候选知识来源，但不应直接当作已审核的业务对象库。选型时先写明是局部对象查询、全局主题总结，还是需要修改业务状态。

本书只核读 R26 的出版机构摘要页，未复现论文实验。不能用论文描述的结果替代本项目的评估。

<a id="ch15--155-模型层应保持可替换"></a>

### 15.5 模型层应保持可替换

无论模型来自本地还是托管服务，建议把访问包、结构化输出、校验和动作服务分开。替换模型时复用相同评估集，检查缺失值、拒答、引用、字段正确性及成本。

教程使用 Ollama 的 `/api/generate` 接口作为可选适配器，发送 JSON Schema 并关闭流式输出。[R30](#references--r30) [R31](#references--r31) 文档注明 Ollama Cloud 暂不支持结构化输出；本教程默认面向本地服务。没有服务时，基线与人工样本模式仍可学习其余机制，但不能用于评价模型质量。

<a id="ch15--156-用小型选型实验代替功能清单打分"></a>

### 15.6 用小型选型实验代替功能清单打分

拿同一份代表性数据完成五件事：导入并保留来源；回答能力问题；拒绝越权与错误输入；处理一次模式迁移；在故障后恢复一次业务请求。记录每项的实现工时、运行成本、延迟、查询表达难度和运维要求。

同时实际导出数据、查询、模型定义和评估资产，检查能否在目标路线恢复。所谓“支持开放格式”需要落实到对象身份、时间、权限和动作语义是否保留。

总拥有成本至少包括许可或云费用、数据工程、建模与审核、平台运维、培训、变更和退出成本。报价和产品能力随版本及合同变化，本书不编造统一价格，也不提供脱离工作负载的“最佳数据库”。

<a id="ch16--第-16-章-交付与持续演进"></a>

## 第 16 章　交付与持续演进

本章目标是把一个可演示的语义应用，变成有人维护、能够升级且可以恢复的服务。本体、源数据、模型与业务规则都会变，交付方案必须管理这些变化之间的依赖。

<a id="ch16--161-用一条工作流形成首次交付"></a>

### 16.1 用一条工作流形成首次交付

首期选择一个业务负责人、一组明确对象和一个可验收任务。设备案例把范围限定为“读取最新可用观测，寻找适用程序，提出维修草稿并取得回执”。它没有同时承诺故障诊断、自动排产和设备控制。

交付可分为四个阶段，时间根据数据条件调整：

| 阶段 | 工作 | 退出条件 |
| --- | --- | --- |
| 定义 | 观察业务、收集反例、确定能力问题与基线 | 任务输入、输出、责任和禁止行为清楚 |
| 只读原型 | 身份映射、数据合同、查询与证据包 | 代表性正常和异常问题可验证 |
| 受控试点 | 建议、审核、动作、回执与故障恢复 | 写入条件、去重和未知状态处理通过验证 |
| 运营交接 | 监控、变更、排障、容量与成本 | 接收团队可独立复现、恢复和升级 |

阶段依据证据推进。一个演示在周五答对了几道题，并不意味着周一就应开放所有写入权限。

<a id="ch16--162-本体变更需要评审影响"></a>

### 16.2 本体变更需要评审影响

新增标签通常影响较小；修改类层级、domain、range、等价关系或身份规则，可能改变大量推理结论。收紧 SHACL 必填项可能阻止历史数据发布；更改程序映射可能改变模型建议和后续动作。

每项变更说明目的、受影响概念、迁移方式、查询兼容性、评估变化和恢复方法。版本号帮助定位，但不能单独表达全部兼容关系，应提供机器可执行的迁移与回归样本。

本体维护不是某位专家在编辑器里保存一个新文件。业务负责人确认含义，数据负责人确认来源映射，应用负责人确认查询与动作，平台负责人确认部署与访问边界。规模较小时一人可以承担多个角色，责任仍应明确。

<a id="ch16--163-分别版本化系统资产"></a>

### 16.3 分别版本化系统资产

建议把本体、形状、数据映射、查询模板、文档版本、模型及提示、输出合同、动作策略和评估集分别标识，并记录某次发布使用的组合。数据快照则需要可定位的时间或版本。

例如，只修改提示语不应悄悄改变批准规则；升级本体也不能使旧提案绕过原有快照检查。发布记录应能回答：“这份草稿是依据哪一版事实、程序、策略和建议产生的？”

本教程的评估报告记录实现摘要、依赖版本、实际运行时间和固定业务时间。动作快照记录对象版本、文档哈希、本体版本和策略版本。这是小规模示例，并未替代生产制品仓库或完整数据血缘系统。

<a id="ch16--164-用扩展迁移收缩处理兼容"></a>

### 16.4 用扩展、迁移、收缩处理兼容

生产环境可先让新版本读取新旧结构，迁移已有数据，核对数量与语义，再停止旧写入，最终移除兼容路径。迁移期间要避免双写产生冲突，并明确失败重试和检查点。

本教程把旧谓词 `legacyAsset` 迁移到 `forAsset`，使用 SPARQL Update 删除旧关系并插入新关系。[R10](#references--r10) 首次运行移动一条关系，再次执行移动零条，旧谓词被标记弃用。文件名中的 v1/v2 表示示例迁移前后；迁移后报告的领域本体版本为 `1.0.0`。

这个演示验证了小型转换的重复执行行为，没有实现在线双写、分布式迁移或自动回滚。真实迁移应增加源目标计数、关键能力问题、约束报告、身份一致性及未迁移记录清单。删除旧公理时还要重新计算派生图，避免旧结论继续生效。

<a id="ch16--165-回滚代码与撤销业务效果是两件事"></a>

### 16.5 回滚代码与撤销业务效果是两件事

代码可以部署回旧版本，已发送的工单或通知却不会因此消失。恢复方案需要分别处理代码、数据、索引、缓存、推理结果和外部业务效果。

数据库备份可恢复历史状态，但可能覆盖之后合法的新记录；外部系统可能需要取消或补偿操作，而不是删除审计轨迹。对无法立即确认结果的请求，应保留未知状态并对账，不应通过重新部署或清空请求表“解决”。

发布前做一次恢复演练：制造失败、接管处理中任务、核对外部回执、恢复服务并确认没有重复效果。恢复成功的证据比一份从未执行过的操作手册更有说服力。

<a id="ch16--166-把运营指标交给具体责任人"></a>

### 16.6 把运营指标交给具体责任人

数据过期告警应指向数据链路负责人，SHACL 违反率上升应能找到源系统与映射变更，未确认动作要有处理时限与负责人。模型成本、人工审核量和本体维护量都应进入日常运营。

交接材料包括部署步骤、能力问题、接口合同、评估运行方式、角色与权限配置、数据与版本关系、故障分类、回滚或补偿流程，以及仍未支持的场景。接收者应亲自完成一次从干净环境启动到故障恢复的操作。

对于 FDE 团队，可把现场发现的问题沉淀为通用对象、映射规则、查询与动作模式，同时保留客户业务差异。复用应减少重复劳动，不应强迫不同业务共享实际上不同的概念。

配套实践见[第 10 课](#lesson10)。

<a id="ch17--第-17-章-设备维修助手完整案例"></a>

## 第 17 章　设备维修助手完整案例

本章把前面的概念连接成一次可运行交付。所有数据均为合成数据，业务动作写入本地模拟器。读者应同时观察结果、约束和失败状态。

<a id="ch17--171-问题与验收"></a>

### 17.1 问题与验收

北厂计划员输入设备编号 `P-101`。系统需要定位当前租户和厂区内的设备，读取最新观测与对象版本，找到有效程序，生成有证据的建议，经批准创建维修工单草稿。

| 情况 | 期望行为 |
| --- | --- |
| 北厂 P-101，92 C，程序有效 | 提出需批准的维修草稿建议 |
| 北厂 P-102，161.6 F | 转换成 72 C，本教学规则下不建议建单 |
| 同名但属于另一租户的 P-101 | 只按可信身份访问相应租户 |
| 北厂身份请求南厂 P-201 | 返回不存在或无权访问，不暴露详情 |
| 观测或对象快照过期 | 请求补充信息，停止提出写入动作 |
| 外部已创建，但返回响应丢失 | 保持未知，通过同请求 ID 对账恢复 |

80 C 只是本教学案例的核查阈值。真实设备的报警标准、程序与人员资格必须来自其领域规则。

<a id="ch17--172-数据模型与服务边界"></a>

### 17.2 数据模型与服务边界

核心类包括设备、泵、离心泵、产线、厂区、观测和程序。每次观测是独立对象，保存时间、单位和值。租户与设备编号共同组成身份，设备名称只供展示。

系统由五个逻辑部分组成：CSV 到 RDF 的导入器；提供授权上下文的图服务；选择文档的检索器；生成和验证建议的组件；保存提案、批准、执行请求并连接外部模拟器的动作服务。

```text
CSV + 本体 ─→ 命名图 ─→ 身份与区域检查 ─→ 当前观测和关系
                                               │
程序文档 ─→ 权限与有效期过滤 ────────────────────┤
                                               ↓
                                         本次证据包
                                               ↓
                                   基线 / 样本 / 可选本地模型
                                               ↓
                                   输出合同与关键字段校验
                                               ↓
                                   提案 → 批准 → 条件执行
                                               ↓
                                   外部草稿回执 / 未知后对账
```

OWL RL 的类型、逆关系与传递关系演示独立展示逻辑蕴含；应用检索本身使用固定关系查询和有界遍历。不能把所有图遍历收益都归为 OWL 推理收益。

<a id="ch17--173-从干净环境启动"></a>

### 17.3 从干净环境启动

安装方式见[教程入口](#tutorial)。完成环境准备后，在 `tutorials/ontology-ai` 目录运行：

```console
python -m ontology_lab doctor
python -m ontology_lab demo
```

默认创建新的 `.runs/demo-...` 目录，报告包含导入、推理、校验、检索、动作、评估和迁移。也可以使用 `--workdir` 指定新目录。已有完整案例目录不会被清空；再次运行时换一个目录，以保留原始执行记录。

基础案例不调用模型。要学习模型输出验证，运行 `generate --mode fixture`；要评价实际模型，另行准备本地 Ollama 服务并使用 `generate --mode live --model 模型名`。三种模式的含义和实测范围必须分开。

<a id="ch17--174-阅读一次正常证据链"></a>

### 17.4 阅读一次正常证据链

P-101 的证据包包含租户 `TENANT-A`、区域 `NORTH`、对象版本 7、92 C 的观测及其时间，图证据 ID 为 `KG:TENANT-A:P-101:v7:OBS-101`。适用程序是 `PROC-PUMP-01`，授权文档是 `MANUAL-N-1`。

文档内容哈希绑定本次使用的程序文本。提案保留设备、温度、时间、程序、证据、文档哈希与策略版本。批准是可信计划员对该具体提案的授权，模型输出的 `requires_approval` 只是建议合同字段。

首次写入前，动作服务复核身份、批准、对象状态、新鲜度和程序。外部模拟业务系统也按其当前对象版本执行条件写入，避免应用读取后、写入前出现变化却仍盲目接受请求。

<a id="ch17--175-亲自观察响应丢失"></a>

### 17.5 亲自观察响应丢失

运行：

```console
python -m ontology_lab actions --scenario timeout
```

报告中，`first_attempt.state` 为 `outcome_unknown`，`same_key_retry.state` 仍为 `outcome_unknown`，对账后的 `final.state` 为 `executed`。外部草稿总数是 1。重复提交没有将“不知道结果”直接改写成“重新创建”。

通过第 08 课的分步命令，还可以停止在未知状态，再由新的进程打开原目录进行对账。执行记录与外部草稿分别存放在不同 SQLite 文件中，用来展示状态持久性与跨系统响应不确定性。

`executed` 只表示该草稿动作取得匹配回执。它不表示正式派工、设备已经停机或故障已修复。若两个不同提案实际上对应同一次异常，还需要额外的异常事件唯一键，当前同提案去重不会自动解决这个业务问题。

<a id="ch17--176-实际得到的结果"></a>

### 17.6 实际得到的结果

在锁定环境中，原始图有 125 条三元组，OWL RL 闭包为 451 条，增加 326 条；类型、逆关系和传递关系检查均通过。新增数量包含规则产生的语义相关三元组，不能解释为发现了 326 条新的业务事实。

有效数据通过 SHACL，故意错误的数据被拒绝；四个检索案例的词项基线命中 2 个，关系增强命中 4 个；超时对账最终只留下一份草稿；迁移首次移动一条关系，再次移动零条。完整原始报告和验证范围见[实测记录](../../tutorials/ontology-ai/reports/verification.md)。

这些结果证明示例按既定合同运行。它们不证明工业诊断能力、生产吞吐量、模型正确率或完整的安全防御能力。本机验证没有调用真实模型或生产业务系统。

<a id="ch17--177-把案例迁移到自己的场景"></a>

### 17.7 把案例迁移到自己的场景

先替换能力问题与评估样本，再替换数据映射。保持可信身份、来源、时间、证据包、输出合同及动作回执这些边界。若只是更换模型而没有定义领域含义，系统仍可能在正确格式里生成错误结论。

接入真实工单系统时，先确认其条件写入、幂等、请求查询和回执语义。没有请求查询能力时，要设计人工核对或业务事件查询路径，不能假设所有接口都像本地模拟器一样支持对账。

<a id="ch18--第-18-章-行业应用与研究前沿"></a>

## 第 18 章　行业应用与研究前沿

本章目标是把工程方法迁移到新领域，同时识别哪些主张已经由标准或实现支持，哪些仍需实验。以下行业场景是设计示例，不是客户案例或效果承诺。

<a id="ch18--181-行业差异首先体现在概念与责任"></a>

### 18.1 行业差异首先体现在概念与责任

| 领域 | 关键对象与关系 | AI 可帮助的任务 | 首要验证条件 |
| --- | --- | --- | --- |
| 制造与维护 | 设备、部件、观测、程序、工单 | 查找适用程序、汇总事件、准备草稿 | 单位、时效、设备身份、人员资格 |
| 供应链 | 订单、物料、库存、批次、交付承诺 | 解释缺货影响、追踪批次、提出调拨 | 时间口径、库存锁定、跨系统状态 |
| 金融运营 | 客户、法人、账户、交易、规则 | 尽调材料归并、异常线索解释 | 实体对齐、证据、规则版本、访问范围 |
| 医疗知识服务 | 病例、观察、诊断、药物、指南 | 获准资料检索、编码辅助、文档整理 | 来源适用性、否定与时间、专业审核 |
| 科研与研发 | 样品、实验、测量、方法、论文 | 追溯结果、组织假设、查找相关实验 | 实验条件、单位、不确定性、可复现性 |
| 企业知识管理 | 产品、团队、项目、文档、决策 | 跨系统定位知识、解释关系与变更 | 权威来源、文档版本、权限与撤回 |

同一个“客户”在营销、合同和财务中可能指联系人、签约主体或付款主体。迁移时应先定义问题中的身份，不能因为标签相同就统一为一个类或对象。

<a id="ch18--182-复用标准词汇同时保留领域语义"></a>

### 18.2 复用标准词汇，同时保留领域语义

SKOS 适合组织术语、标签及概念之间的语义关系；PROV-O 提供实体、活动和参与者等来源表达；OWL-Time 表达时间概念；SOSA/SSN 支持传感器、观测及相关实体的建模。[R13](#references--r13) [R14](#references--r14) [R15](#references--r15) [R16](#references--r16)

复用时记录采用的版本、使用子集和映射依据。外部词汇的类定义若与本地业务不完全一致，可以建立较弱映射或应用层转换，而不是随意添加等价公理。

本教程采用自定义小模型方便阅读，并没有实现完整 SOSA、PROV 或工业标准模型。扩展时可以先把观测映射到 SOSA 概念，再用能力问题检查是否保留设备、时间、测量对象与单位，逐步迁移，避免一次引入大量无法解释的术语。

<a id="ch18--183-大模型辅助本体工程"></a>

### 18.3 大模型辅助本体工程

模型可以从资料中提出术语候选、类层级、能力问题、映射和测试反例，也可以解释本体变更。它降低草拟成本，但可能产生同义重复、含糊定义、不恰当等价关系或与用途无关的复杂结构。

较稳妥的流程是：提供任务范围与来源；让模型输出候选及依据；由领域人员确认含义；用逻辑与约束检查；运行能力问题；最后合并版本。模型提出的新概念应能说明它支持哪项查询或工作流。

评价这种辅助时，不只计算生成了多少类，还要测量审核工时、接受率、回归错误、后续维护成本和能力问题覆盖度。自动产生庞大本体可能增加而不是减少知识债务。

<a id="ch18--184-从知识图谱到神经符号协作"></a>

### 18.4 从知识图谱到神经符号协作

关于大模型与知识图谱的路线研究，讨论了用知识图谱增强模型、用模型辅助图谱，以及二者协作的方向。[R29](#references--r29) 《Knowledge Graphs》提供了图数据模型、查询、逻辑、学习与应用的系统性讨论。[R28](#references--r28)

这些方向不意味着存在一种能解决所有任务的统一架构。概率预测、逻辑蕴含、规则决策与业务授权具有不同含义。模型认为某关系很可能成立，可以推动审核；逻辑系统推出某类型，依赖其前提与语义；业务动作能否执行，还依赖身份和当前状态。

本书对 R29 只核读作者摘要页，未据此报告算法细节或实验优势。研究路线可作为探索地图，具体技术仍需要完整文献阅读和独立实验。

<a id="ch18--185-值得继续探索的工程问题"></a>

### 18.5 值得继续探索的工程问题

第一，时间与版本如何参与知识检索和推理。许多事实在一段时间内成立，历史解释与当前动作需要不同的快照；简单覆盖旧值会破坏追溯。

第二，如何维护派生知识。来源撤回或身份纠正后，哪些摘要、推理结果、向量索引和提案需要失效？规模扩大时，依赖追踪与增量维护会成为主要成本。

第三，如何校准不确定性。来自传感器、人工记录、模型抽取和链接预测的置信度含义不同，不能简单放到一个数值字段里排序。应明确每个概率对应什么事件，如何估计和验证。

第四，如何在知识与动作之间保持可审计的联系。系统不仅要解释“为何推荐”，还要说明“谁批准了什么”“执行时依据是否仍有效”“外部效果如何确认”。这通常比聊天界面的生成质量更决定生产可用性。

<a id="ch18--186-给读者的下一项项目"></a>

### 18.6 给读者的下一项项目

选择一个自己的能力问题，准备十余条有代表性的正常、缺失、冲突和越权样本。先建立简单基线，再增加最少的概念和关系。记录新增维护成本，并比较相同数据条件下的任务结果。

只读任务稳定后，再决定是否增加业务动作。每增加一个动作，就明确输入、身份、前提、批准、外部效果、幂等和对账。每增加一项本体公理，就说明它带来的查询或推理收益，以及可能改变的结论。

本体的价值最终体现在可解释、可维护的任务改进中。读者应能够回答：哪些含义由领域人员定义，哪些事实来自数据，哪些结论由规则推出，哪些建议由模型生成，哪些操作已经得到外部确认。

<a id="answers--习题参考答案"></a>

## 习题参考答案

以下对应正文每章的两道思考题，共 36 题。参考答案强调判断条件和验证方法；在不同业务约束下，可以存在其他合理设计。

<a id="answers--第-01-章"></a>

### 第 01 章

<a id="answers--011-扫描识别错误是否需要复杂本体"></a>

#### 01.1 扫描识别错误是否需要复杂本体

先抽样追踪错误链路，区分 OCR 字符错误、版面还原、切分、检索和生成问题。若设备编号被识别错，增加本体未必恢复正确身份，可能把错误值连接到另一对象。应先改善识别和来源定位，建立简单检索基线；当主要剩余错误确实来自概念不一致或跨来源关系时，再验证本体投入。

<a id="answers--012-表和字段画成图后还缺什么"></a>

#### 01.2 表和字段画成图后还缺什么

还缺用途、概念定义、稳定身份、关系含义与方向、时间和来源规则，以及能验证价值的能力问题。数据库表可能只是存储结构，不对应业务实体。应选一条真实任务，比较图表示是否降低误解或支持原先困难的查询，同时明确维护责任。

<a id="answers--第-02-章"></a>

### 第 02 章

<a id="answers--021-从未维修需要哪些前提"></a>

#### 02.1 “从未维修”需要哪些前提

至少明确观察时间范围、设备身份连续性、哪些事件算维修、涵盖哪些系统，以及记录是否完整。系统中查不到记录，只能得出“在该数据范围内未发现登记事件”。若历史迁移或外包维修未纳入，就不能推出从未维修。可将完整性状态随答案返回，必要时拒绝作全历史判断。

<a id="answers--022-把销售目标改成能力问题"></a>

#### 02.2 把销售目标改成能力问题

例如：“当前用户负责的客户 A 在本季度有哪些已签合同？”正常返回授权合同及版本，身份歧义时澄清；“哪些交付承诺将在七天内到期？”正常返回约定时区下的订单与期限，数据过期时提示补充；“客户最近一次确认的需求来自哪份记录？”正常返回来源和时间，只有模型推测而无原始记录时不作确定回答。每题都限定了对象、范围和证据。

<a id="answers--第-03-章"></a>

### 第 03 章

<a id="answers--031-为什么要把观测建成独立对象"></a>

#### 03.1 为什么要把观测建成独立对象

只保存设备到温度值的关系，会丢失每次测量的时间、单位、来源和传感器信息。相同数值的重复三元组在 RDF 图中也不会形成多次事件。独立观测使用观测 ID，关联设备、测量时间与结果；“当前温度”由明确的有效性和最新记录规则导出。

<a id="answers--032-文件图结构和业务含义的比较"></a>

#### 03.2 文件、图结构和业务含义的比较

文件 SHA-256 比较字节版本；空白节点标签变化或排序变化都可能导致不同。图同构检查可判断空白节点重新命名后的结构是否等价；数据集规范化可支持可重复摘要，但应选定算法与范围。即使结构不同，业务查询结果也可能相同；这需要在选定语义和能力问题下分析，不能由单一哈希推断。

<a id="answers--第-04-章"></a>

### 第 04 章

<a id="answers--041-函数属性为什么不一定报重复错误"></a>

#### 04.1 函数属性为什么不一定报重复错误

在相关 OWL 语义下，一个函数对象属性的两个目标可能被推为同一个体；不同名字不自动代表不同实物。若业务要求只接受一个明确责任人记录，可用 SHACL 的数量约束或业务服务校验，并维护身份映射。需要声明个体不同或检查逻辑一致性时，应单独建模，不能把输入校验与同一性推理混为一谈。

<a id="answers--042-必须有传感器但没有记录"></a>

#### 04.2 必须有传感器但没有记录

OWL 的存在限制表达某个传感器存在，不一定产生一个可查询的具体名称，也不必因记录缺失而报错。SHACL 可以要求数据中有相应关系和值。业务执行还需确认传感器身份、有效观测、校准状态及新鲜度；即使图中补了一个空节点满足结构，仍不足以支持真实操作。

<a id="answers--第-05-章"></a>

### 第 05 章

<a id="answers--051-静态合格为什么不能代替新鲜度"></a>

#### 05.1 静态合格为什么不能代替新鲜度

SHACL 校验是在给定图与形状下进行的，时间推进后“最新”可能已经不满足任务要求。首次写入应使用可信时钟重新检查观测、对象与程序有效期；过期时重新获取或停止。校验报告可记录当时状态，但不能无期限当作执行通行证。

<a id="answers--052-闭合形状拒绝来源字段怎么办"></a>

#### 05.2 闭合形状拒绝来源字段怎么办

先看来源字段是否属于合法合同。如果需要保留，就明确加入允许属性、配置忽略项，或拆分来源图与业务数据图。如果源字段确实错误，应修复映射。收紧形状前评估历史数据与下游消费者，发布兼容期；不应为了让报告变绿删除有价值的来源证据。

<a id="answers--第-06-章"></a>

### 第 06 章

<a id="answers--061-本月高风险设备怎样表示"></a>

#### 06.1 “本月高风险设备”怎样表示

通常适合作为带评估时间、规则版本、依据和有效期的评估结果，或在条件简单时作为查询集合。“设备”的稳定类体系与月度风险判断分开，能保留历史解释。如果确需定义风险类，应说明成员如何随时间更新、旧推断如何撤回，避免把暂时状态永久化。

<a id="answers--062-同名循环泵为何不能直接-sameas"></a>

#### 06.2 同名循环泵为何不能直接 sameAs

名称可能指产品类别、型号或不同实物。同一性判断应核对制造商序列号、租户、安装地点、生命周期及权威映射。证据不足时使用候选匹配或较弱关联，记录来源和审核状态。错误 sameAs 可能传播属性与权限相关信息，影响远超一次搜索排序。

<a id="answers--第-07-章"></a>

### 第 07 章

<a id="answers--071-昨天观测今天导入采用哪个时间"></a>

#### 07.1 昨天观测、今天导入采用哪个时间

当前维修建议主要依据观测发生时间判断测量是否新鲜，同时检查设备主数据快照时间。导入时间说明数据链路延迟，不会使旧测量重新变新。还可保留源系统提交时间、有效时间、处理时间、来源版本与处理活动，以区分迟到、修订和回补。

<a id="answers--072-删除公理后怎样清理派生结果"></a>

#### 07.2 删除公理后怎样清理派生结果

小规模系统可以保留断言图，丢弃并重新构建派生图，运行能力问题和约束回归后切换版本。大规模系统需要依赖追踪、增量撤回或分区重算，并检查结论是否仍有其他支持路径。索引、摘要与缓存也需按版本失效，不能只删除本体文件中的一行。

<a id="answers--第-08-章"></a>

### 第 08 章

<a id="answers--081-两个标签乘三个观测为什么有六行"></a>

#### 08.1 两个标签乘三个观测为什么有六行

连接模式产生标签与观测的组合，六行并不意味着六台设备。计数可使用 `COUNT(DISTINCT ?asset)`；展示应限制语言、选择有效最新观测或分开查询。具体方法取决于要统计实体、事件还是组合，不能习惯性地用行数代表业务数量。

<a id="answers--082-select-前缀为什么不构成完整安全边界"></a>

#### 08.2 SELECT 前缀为什么不构成完整安全边界

查询仍可能访问不该读取的命名图、使用远程 `SERVICE` 或执行昂贵路径与连接。应限制可访问端点和图、允许的查询模板、参数与资源预算，并配置网络出口和超时。文本前缀检查既不能解析完整语义，也不能限制查询带来的间接访问。

<a id="answers--第-09-章"></a>

### 第 09 章

<a id="answers--091-过期关系为何可能让结果更差"></a>

#### 09.1 过期关系为何可能让结果更差

图关系能找回措辞不重合的正确程序，也可能以高优先级召回旧程序。应按关系正确、缺失、过期、冲突及权限边界分层，固定检索预算，测量命中、错误证据与拒答。增加关系更新责任、文档有效期和冲突处理，再评价净收益。

<a id="answers--092-为什么-44-不代表模型准确率-100"></a>

#### 09.2 为什么 4/4 不代表模型准确率 100%

四条是人工设计检索案例，数量小且不是独立抽样；指标是首条文档命中，不是生成正确率；实验没有调用模型；基线是词项重合而非全部检索路线；输入已经给出设备编号。任何一项都限制外推，应原样报告机制、分母和未测范围。

<a id="answers--第-10-章"></a>

### 第 10 章

<a id="answers--101-怎样保留怀疑的语气"></a>

#### 10.1 怎样保留“怀疑”的语气

候选记录应保存原文片段、来源位置、主体候选、陈述类型“假设”、提出者和时间，接受状态为待核实。可以记录“某记录提出轴承损坏假设”，但不能直接写成已确认故障。确诊需要另一条有依据的事件或审核结果，并保留两者关系。

<a id="answers--102-结构与引用-id-正确仍可能错在哪里"></a>

#### 10.2 结构与引用 ID 正确仍可能错在哪里

第一，引用确实存在，但文本只说“核查传感器”，摘要却声称“轴承已损坏”；需要陈述级支持审核。第二，引用来自同一设备的历史版本，不能支持当前温度或程序；需要检查时间、版本和适用范围。ID 存在只是必要条件，不能代替证据与结论的对应关系。

<a id="answers--第-11-章"></a>

### 第 11 章

<a id="answers--111-本地去重为何仍可能重复外部效果"></a>

#### 11.1 本地去重为何仍可能重复外部效果

外部成功创建工单后响应丢失，本地只知道超时。若重建请求记录或生成新外部请求 ID 后再提交，外部可能再次创建。本地与外部需要稳定关联键、外部幂等或可查询回执；未知状态应对账，不应直接重发。不能仅凭没有本地成功回执推断没有外部效果。

<a id="answers--112-换键与同事件的不同提案"></a>

#### 11.2 换键与同事件的不同提案

相同提案换幂等键时，可通过提案唯一性找到原操作并返回同一状态，避免新增效果。不同提案若对应同一次异常，需要异常事件 ID、有效工单范围或活动工单唯一约束。提案内容相似度只能辅助人工合并，不能替代清晰业务唯一性规则。

<a id="answers--第-12-章"></a>

### 第 12 章

<a id="answers--121-098-的预测为何不是逻辑蕴含"></a>

#### 12.1 0.98 的预测为何不是逻辑蕴含

它是某模型在特定训练和校准条件下的评分或概率，可能错误或分布外失效。逻辑蕴含则依据公理、事实和语义。预测可进入候选图，携带模型版本、证据和审核状态；通过明确接纳流程后才能作为权威前提，且仍需处理撤回。

<a id="answers--122-怎样判断多智能体是否必要"></a>

#### 12.2 怎样判断多智能体是否必要

用固定三步工作流作基线，在相同任务、数据、工具与预算下比较成功率、异常恢复、人工干预、成本和延迟。另设需要动态规划的任务层，观察收益是否仅出现在复杂样本。若协商主要增加轮数和不稳定性，可保留确定流程，只在真正不确定的步骤使用模型。

<a id="answers--第-13-章"></a>

### 第 13 章

<a id="answers--131-原数据有权限为何摘要仍泄漏"></a>

#### 13.1 原数据有权限为何摘要仍泄漏

摘要已经成为新的派生资产，原始行级权限不一定自动跟随到共享索引。需要按接收者范围存储或重新授权，保留来源依赖，处理撤权与删除，并将过滤放在模型上下文形成之前。不能把生成者有权读取误解为所有人有权接收其总结。

<a id="answers--132-只读-service-的风险"></a>

#### 13.2 只读 SERVICE 的风险

它可能触达内部或外部网络、携带查询中的敏感信息，或触发高成本远程连接和结果扩张。应限制服务地址、网络出口、查询模板、返回大小和执行时间，并验证用户的数据范围。只读主要描述数据修改能力，不代表没有外传或资源风险。

<a id="answers--第-14-章"></a>

### 第 14 章

<a id="answers--141-怎样分离本体的贡献"></a>

#### 14.1 怎样分离本体的贡献

固定数据、模型和检索预算，依次比较基线、仅加关系、仅加重排、关系加重排，再在同一配置上更换模型。保留独立评估集，按关系质量与任务类型分层，同时记录成本。若多个组件有交互作用，应报告组合收益，避免把总提升全部归于一个组件。

<a id="answers--142-高平均成功率为何仍可能不上线"></a>

#### 14.2 高平均成功率为何仍可能不上线

重复工单的损失可能远高于普通回答失败，平均值会掩盖严重少数事件。需单列重复效果、未授权执行、未知状态持续时间和恢复能力，并设置写入门槛。可先限制为只读或草稿审核试点，在幂等与对账未验证前不扩大自动执行范围。

<a id="answers--第-15-章"></a>

### 第 15 章

<a id="answers--151-属性图增加适配层还是换存储"></a>

#### 15.1 属性图增加适配层还是换存储

先用代表性对象验证双向映射是否保留身份、关系属性、时间与所需语义，再运行必须支持的 OWL 推理和查询。比较同步延迟、重复存储、运维、团队技能及退出成本。少量批量交换可能适合适配层；若标准语义与持续推理成为核心负载，RDF 原生路线可能更简洁。结论来自实验，不来自格式名称。

<a id="answers--152-为什么-owl-导出不足以迁移-foundry-应用"></a>

#### 15.2 为什么 OWL 导出不足以迁移 Foundry 应用

还需迁移数据映射和更新机制、对象与链接身份、查询、应用界面、动作参数与提交条件、权限、批准、外部集成、回执、运行历史及评估。部分平台概念没有直接 OWL 对应，必须明确等价实现或已知损失。导出概念只是应用迁移的一部分。

<a id="answers--第-16-章"></a>

### 第 16 章

<a id="answers--161-字段名未改为何仍不兼容"></a>

#### 16.1 字段名未改为何仍不兼容

消费者可能仍把数值当华氏度，产生实际判断错误。应显式记录单位，增加新字段或版本化合同，提供转换和兼容期，回填时保留原始值及来源。用边界值、混合单位和历史记录验证，更新下游规则后再停止旧语义。

<a id="answers--162-错误工单的恢复步骤"></a>

#### 16.2 错误工单的恢复步骤

先停止受影响的新写入，定位版本和操作 ID；核对外部实际工单，保留审计；由获准人员按业务规则取消、标记或补偿；回滚有问题实现并修复数据、索引或策略；重新跑故障回归并确认所有未决请求。应用回滚不会自动撤销已有业务效果，不应删除记录制造“未发生”的假象。

<a id="answers--第-17-章"></a>

### 第 17 章

<a id="answers--171-owl-演示与检索收益的因果关系"></a>

#### 17.1 OWL 演示与检索收益的因果关系

当前程序关系已显式存在，检索通过固定查询与遍历读取它；运行 OWL RL 的命令独立展示类型、逆关系和传递关系。要测推理贡献，应设计只有派生关系才能回答的能力问题，在相同查询条件下比较断言图与闭包图，并检查额外延迟和错误前提的影响。

<a id="answers--172-外部接口没有幂等和查询能力怎么办"></a>

#### 17.2 外部接口没有幂等和查询能力怎么办

自动重试无法保证不重复。可保留未知状态，停止自动重发，通过业务字段、人工核对或新增集成能力确认效果；必要时把自动化缩减为生成经审核的提交草稿。还应推动外部系统增加唯一业务键或请求记录。无法确认的效果不能被本地状态机“推断成功”。

<a id="answers--第-18-章"></a>

### 第 18 章

<a id="answers--181-从维修迁移到医疗资料服务"></a>

#### 18.1 从维修迁移到医疗资料服务

可复用身份、来源、时间、候选与已接受知识分区、输出合同、审核和对账的工程思想。患者身份、诊断、药物、否定、适用人群与专业决策责任必须重新建模，设备温度阈值和维修动作不能移植。先限定资料检索任务，使用真实领域规范与专业审核建立评估。

<a id="answers--182-如何评价自动生成的-500-个类"></a>

#### 18.2 如何评价自动生成的 500 个类

统计它们支持了哪些能力问题，审核后接受了多少，是否出现重复、矛盾和错误公理，以及净节省多少专家时间。抽样检查定义与来源，运行回归，再追踪维护成本。可以用更小的人工模型作基线；类数量是产出规模，不是质量或业务价值。

<a id="tutorial--本体与-ai10-课可运行教程"></a>

## 本体与 AI：10 课可运行教程

配套书籍：[《本体在 AI 中的应用：原理、工程与实战》](#book-title)。从 CSV 开始，完成 RDF 建模、查询、推理、校验、授权检索、结构化建议、批准与业务对账。

所有设备与身份都是合成数据。唯一业务动作是在本地独立 SQLite 模拟系统中创建维修工单草稿。核心课程安装依赖后可离线运行，不需要 Foundry 账号或模型服务；真实模型调用是第 07 课的显式可选步骤。

<a id="tutorial--环境准备"></a>

### 环境准备

实测环境为 Windows、Python 3.11.0。建议使用 Python 3.11 创建独立环境，其他系统和 Python 版本需要自行验证。先克隆仓库，再进入本教程目录：

```console
git clone https://github.com/tanghama-aol/fde.git
cd fde/tutorials/ontology-ai
```

Windows PowerShell：

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
.\.venv\Scripts\Activate.ps1
python -m ontology_lab doctor
```

如果本机策略不允许激活脚本，无需修改系统策略；将后续命令中的 `python` 替换为 `.\.venv\Scripts\python.exe` 即可。

macOS / Linux：

```sh
python3.11 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-lock.txt
python -m ontology_lab doctor
```

[requirements.txt](../../tutorials/ontology-ai/requirements.txt)列出直接依赖，[requirements-lock.txt](../../tutorials/ontology-ai/requirements-lock.txt)锁定实测环境的完整版本，也包含电子书构建所用的 Markdown 解析库。安装通常需要网络；版本锁定不等于所有平台二进制包均已验证。

<a id="tutorial--先跑完整案例"></a>

### 先跑完整案例

```console
python -m ontology_lab demo
python -m unittest discover -s tests -v
```

`demo` 创建新的 `.runs/demo-...` 目录，保存报告、导入图、迁移结果及模拟业务数据库。验证范围与原始结果见[实测记录](../../tutorials/ontology-ai/reports/verification.md)。本版实测 40 项测试通过；真实模型调用数与生产系统调用数均为 0。

所有子命令都支持 `--output 文件名.json`。`actions`、`ingest`、`migrate`、`demo` 可通过 `--workdir` 指定输出目录；动作和完整案例不覆盖已有执行状态。重复学习时使用新目录，已有目录留作对账和比较。

### 固定业务时钟

案例的“现在”固定为 `2026-09-01T09:02:00Z`；设备和观测快照为 `09:00:00Z`，允许新鲜度为 300 秒。这样不同日期运行课程会得到相同业务判断。报告仍记录实际运行时间。真实系统应使用可信实时时钟，而不是照搬教学时间常量。

<a id="tutorial--常见问题"></a>

### 常见问题

`No module named ontology_lab` 通常表示当前目录错误，应进入 `tutorials/ontology-ai`。依赖导入失败时，检查安装依赖和运行代码是否使用同一个 Python。Windows 控制台中文显示异常，可使用 `python -X utf8 -m ontology_lab ...`。

`RUN_EXISTS` 表示已有运行状态被保留，换用新的 `--workdir`，不要为了重跑而清空原请求记录。`NOT_FOUND_OR_FORBIDDEN` 是预期权限行为，不能据此区分对象不存在还是无权访问。真实模型服务不可用时只影响 `generate --mode live`，不会转成执行业务动作。

<a id="tutorial--从教程到生产的差距"></a>

### 从教程到生产的差距

固定 `Principal` 是身份系统替身；本地文件可被操作者直接读取，文件布局不构成多租户隔离。RDFLib 内存图与 SQLite 用于小规模教学，没有验证生产负载或高可用。输出校验只覆盖结构及若干关键字段，不证明自由文本每句话都正确。跨租户、过期、异常回执等测试验证已知边界，不构成完整安全认证。

把案例接入真实系统前，应重新建立领域标准、身份服务、数据质量、评估集、动作合同与运维责任，详见书籍第 13—17 章。

<a id="lesson02--第-02-课-rdf-与-sparql"></a>

## 第 02 课　RDF 与 SPARQL

目标：把源数据理解为带身份的图，并区分管理员教学查询与最终用户的授权查询。对应书籍第 03、08 章。

<a id="lesson02--操作"></a>

### 操作

```console
python -m ontology_lab rdf
```

`assets` 中应有甲公司三台设备：P-101、P-102、P-201；`named_graphs` 列出两个租户图；`default_union` 为 `false`。这条命令是管理员视角的合成数据教学演示，故意没有按北厂用户过滤 P-201。最终用户访问边界在第 06 课演示。

阅读[本体](../../tutorials/ontology-ai/data/ontology.ttl)与[查询](../../tutorials/ontology-ai/queries/assets.rq)。关键模式为：

```sparql
?asset rdf:type/rdfs:subClassOf* ex:Asset ;
       ex:assetId ?assetId ;
       ex:region ?region ;
       ex:version ?version .
```

<a id="lesson02--解释"></a>

### 解释

这里从对象的显式类型出发，沿零次或多次 `subClassOf` 找到 Asset。它是 SPARQL 属性路径查询，本身不代表已经运行完整 OWL 推理。程序可以在没有预先物化所有父类类型的图上查到离心泵。

`https://example.org/data/TENANT-A/asset/P-101` 是设备身份；“北厂循环泵”是带中文语言标签的名称。命名图组织租户数据，但图名不会自动拒绝越权请求。应用必须决定哪个用户能查询哪个图及哪些对象。

结果行不是天然的实体计数。一台设备若有多种标签和多条观测，连接查询可能返回多行，统计时应明确去重与最新记录规则。

<a id="lesson02--常见失败"></a>

### 常见失败

把图数据库中的默认图误当成所有命名图的并集，可能导致查询为空或查询范围扩大。本教程显式关闭默认并集。把所有关系替换为简单字符串，也会丢失稳定身份与可连接性。

<a id="lesson02--练习"></a>

### 练习

复制查询为自己的实验文件，给模式加入 `FILTER(?region = "NORTH")`。预期甲公司剩两台设备。说明为什么固定区域筛选仍不能替代可信身份授权：用户可否选择其他区域，必须由服务端决定。

## 第 03 课　逻辑推理

目标：观察类型、逆关系和传递关系的物化结果，理解逻辑推理的前提。对应书籍第 04、12 章。

<a id="lesson03--操作"></a>

### 操作

```console
python -m ontology_lab reason
```

锁定数据与依赖下，输出的重要字段为：

```json
{
  "asserted_triples": 125,
  "closure_triples": 451,
  "added_triples": 326,
  "asserted_asset_type": false,
  "inferred_asset_type": true,
  "inferred_inverse": true,
  "inferred_transitive_part": true
}
```

查看[graph.py](../../tutorials/ontology-ai/ontology_lab/graph.py)中的 `infer`。它复制输入图，然后调用 OWL RL 闭包扩展，保留原始图不变。

<a id="lesson03--解释"></a>

### 解释

P-101 显式类型为 `CentrifugalPump`。通过 `CentrifugalPump → Pump → Asset` 得到 Asset 类型。设备 `partOf` 产线，产线 `partOf` 厂区；`partOf` 被声明为传递属性，所以得到设备属于厂区。`hasPart` 是逆属性，因此产线包含设备。

增加 326 条三元组不等于发现 326 条新的业务事实，其中包含规则物化产生的模式与语义相关语句。结果还会受依赖版本和数据内容影响。最重要的检查是预期蕴含是否出现、输入图是否保持不变。

本教程使用 OWL RL 规则物化，不是完整 OWL 2 DL 推理器，未生成推理证明树。缺少某条记录，也不能依照开放世界语义直接推断其否定。

<a id="lesson03--常见失败"></a>

### 常见失败

把 `rdfs:range ex:Asset` 当成拒绝输入的规则，会误解输出：推理器可能给目标节点补上 Asset 类型。希望报错时，应定义数据合同并校验，见下一课。

<a id="lesson03--练习"></a>

### 练习

在一份临时本体中移除 `owl:TransitiveProperty`，保持其他事实不变，再比较目标关系是否仍会被推导。解释为什么两个源关系存在，不代表所有谓词都允许传递；“与某人认识”就不能默认具有这种性质。

## 第 04 课　SHACL 校验

目标：读取有效与无效图的校验报告，判断错误发生在哪个节点与属性。对应书籍第 05 章。

<a id="lesson04--操作"></a>

### 操作

```console
python -m ontology_lab validate
```

应看到 `valid_fixture.conforms: true`、`deliberately_invalid_fixture.conforms: false` 和 `expected_behavior: true`。因为拒绝故意错误数据本身就是成功结果，该演示整体正常退出。

打开[shapes.ttl](../../tutorials/ontology-ai/data/shapes.ttl)和[invalid.ttl](../../tutorials/ontology-ai/data/invalid.ttl)。报告里的每条违反包含：

| 字段 | 含义 |
| --- | --- |
| focus | 被检查且违反约束的节点 |
| path | 出问题的属性路径 |
| component | 触发的 SHACL 约束类型 |
| message | 校验器生成的说明 |

<a id="lesson04--解释"></a>

### 解释

错误样本包含缺少设备版本、错误单位和非 decimal 的观测值。一个错误值可能同时违反数据类型与数值范围，因此违反条目数不等于错误对象数。

本教程向校验器显式传入已解析的 RDF 图，并指定 `inference="rdfs"`。形状目标、类层级和推理配置共同决定哪些节点接受校验；不应省略配置后假设所有引擎给出相同结果。

静态校验通过只说明这个图在当前形状与配置下符合合同。它没有验证温度传感器是否校准正确，也不能保证十分钟后记录仍然新鲜。

<a id="lesson04--常见失败"></a>

### 常见失败

`sh:datatype xsd:decimal` 对 RDF 字面量类型有要求，不能仅凭显示值“像数字”判断合格。排查时同时看词法值与 datatype。若引入闭合形状，原本合法的来源字段也可能被拒绝，需要先明确允许字段及演进方式。

<a id="lesson04--练习"></a>

### 练习

复制错误样本，在副本中补齐版本、改为 decimal 值及摄氏度单位，用 `validate_graph` 校验副本。说明哪些修改是在修复表示，哪些需要回到源系统核实。不能为了通过校验随意编造缺失版本或测量值。

## 第 05 课　数据导入与来源

目标：生成可交换的图数据，观察身份、单位、时间与来源摘要。对应书籍第 07 章。

<a id="lesson05--操作"></a>

### 操作

```console
python -m ontology_lab ingest --workdir .runs/ingestion-lesson
```

目录中产生 `dataset.trig` 与 `ingestion-manifest.json`。报告中的 `p102_temperature_c` 应为 `72.0`。对照华氏度转换公式：`(161.6 - 32) × 5 / 9 = 72`。

用编辑器查看 TriG 文件，定位两个命名图、P-102 的独立观测和 `xsd:decimal` 值。三元组输出顺序可以改变，不影响图结构。

<a id="lesson05--解释"></a>

### 解释

导入器用租户与业务编号构造身份，拒绝重复设备键或重复观测键；观测必须关联到同租户的设备。未知单位、无时区时间以及非有限数值不能静默接受。

清单保存源 CSV 文件的 SHA-256。它表示文件字节版本，不是 RDF 语义规范化摘要；调整 CSV 行顺序或换行，也可能改变文件哈希。需要判断图是否等价时，应另用图同构或适当规范化方法。

数据中保留观测发生时间和设备快照时间。生产环境通常还需要导入时间、源系统版本、处理活动和错误隔离区。本例是自定义 CSV 映射，并未实现 R2RML 或完整 PROV 来源管理。

<a id="lesson05--常见失败"></a>

### 常见失败

复制一行设备后得到 `DUPLICATE_KEY` 是预期行为。时间字符串没有 `Z` 或时区偏移会被拒绝，程序不会猜测服务器本地时区。输入新枚举前应先定义映射规则。

<a id="lesson05--练习"></a>

### 练习

在源文件副本中制造重复键、未知单位和无时区时间，分别说明应修复来源、修改映射还是进入人工处理。可以通过 `build_dataset(assets_path=..., observations_path=...)` 传入副本；不要改坏后续课程共用的数据。

## 第 06 课　授权检索与程序关系

目标：在同一任务上比较词项重合和关系辅助检索，并验证区域访问边界。对应书籍第 09、13 章。

<a id="lesson06--操作"></a>

### 操作

```console
python -m ontology_lab retrieve --asset P-101 --query P-101 --mode lexical --top-k 1
python -m ontology_lab retrieve --asset P-101 --query P-101 --mode graph --top-k 1
python -m ontology_lab retrieve --asset P-201 --query P-201
```

前两条命令的首条文档应分别为 `CATALOG-N-1` 与 `MANUAL-N-1`。第三条返回 `NOT_FOUND_OR_FORBIDDEN`，退出码为 2：北厂身份不能访问南厂 P-201。这里的失败是预期验证结果。

<a id="lesson06--解释"></a>

### 解释

资产目录含 P-101 编号，因此词项重合检索优先选它；真正维修程序没有该设备编号。关系模式沿设备 `usesProcedure` 找到 `PROC-PUMP-01`，把相应获准、有效的文档排在前面。

两个模式都检查文档租户、区域和有效期。关系模式没有特殊权限。沿设备上级关系遍历时，也需要逐节点检查范围与深度，避免通过一条链接绕过对象权限。

证据包还包含结构化温度、版本、时点和 `missing_information`。只读到资产目录、没有取得适用程序时，不能把目录当作维修步骤的依据。

本例输入显式资产编号，词项算法不是向量检索；固定程序关系的排序规则也不是通用 GraphRAG 引擎。可以观察具体机制，不能据此比较所有检索产品。

<a id="lesson06--常见失败"></a>

### 常见失败

把 `--top-k` 调得很大可能让两种模式都包含手册，但首位、上下文成本与错误文档仍不同。评价时应固定结果预算。`rdf` 命令能够看到南厂设备，是因为它属于管理员教学演示；不要把它开放成最终用户接口。

<a id="lesson06--练习"></a>

### 练习

把查询文本改成程序标题，再比较结果；解释为什么关系增强并非对每条问题都带来改进。设计一条“程序关系过期”的反例，写明需要怎样更新关系、过滤旧文档和测量错误率。

<a id="lesson07--第-07-课-结构化建议与可选模型"></a>

## 第 07 课　结构化建议与可选模型

目标：区分模板、人工样本与真实模型输出，并理解 JSON 合法和业务正确之间的差距。对应书籍第 10、12 章。

<a id="lesson07--先运行无需模型的模式"></a>

### 先运行无需模型的模式

```console
python -m ontology_lab generate --mode baseline
python -m ontology_lab generate --mode fixture
python -m ontology_lab generate --mode baseline --asset P-102
```

前两条针对 P-101，预期 `decision: propose`、`temperature_c: 92.0`、`requires_approval: true`，候选动作是 `createMaintenanceDraft`。第三条针对 P-102，预期 `decision: no_action`、72 C、无候选动作。

`run.mode` 分别说明规则模板与人工参考样本；它们的 `live_llm_calls` 都是 0。人工样本固定对应 P-101，不能改成其他资产后仍期待通过事实匹配。

<a id="lesson07--接入自己准备的本地模型"></a>

### 接入自己准备的本地模型

本步骤可选。先安装、启动 Ollama，并准备支持所需输出能力的模型。用 `ollama list` 查看本地模型名称，然后把下面占位名称替换为实际名称：

```console
python -m ontology_lab generate --mode live --model YOUR_LOCAL_MODEL --timeout 120
```

默认地址是 `http://127.0.0.1:11434`。适配器调用 `/api/generate`，发送 JSON Schema，设置 `stream=false`，接收后再次进行客户端校验。配置远程地址需要显式 `--base-url` 和 `--allow-remote`；地址由操作者确定，不能来自模型输出或文档。

官方资料：[结构化输出](https://docs.ollama.com/capabilities/structured-outputs)、[生成接口](https://docs.ollama.com/api/generate)。本书核读时，官方说明 Ollama Cloud 暂不支持结构化输出，不能把本地步骤直接外推到云端。

本版实际验证未调用真实模型。本机没有运行中的 Ollama 服务；协议与错误处理使用本地 HTTP 测试桩验证，不是模型能力测试。

<a id="lesson07--检查合同和事实"></a>

### 检查合同和事实

阅读[输出合同](../../tutorials/ontology-ai/data/recommendation.schema.json)及 `validate_recommendation`。校验器限制字段与枚举，并复核资产、温度、程序、证据和动作前提。模型不能添加管理员角色或自己签发批准。

可以在 Python 交互环境中执行以下反例：

```python
from ontology_lab.common import DATA, NORTH_PLANNER, LabError, read_json
from ontology_lab.retrieval import Retriever
from ontology_lab.generation import validate_recommendation

bundle = Retriever().bundle(NORTH_PLANNER, "P-101", "P-101")
candidate = read_json(DATA / "recommendation.fixture.json")
candidate["temperature_c"] = 999
try:
    validate_recommendation(candidate, bundle)
except LabError as error:
    print(error.code)  # FACT_MISMATCH
```

<a id="lesson07--常见失败"></a>

### 常见失败

`MODEL_UNAVAILABLE` 表示服务错误或超时，不会转而创建业务记录。`OUTPUT_SCHEMA` 表示结构不合约；`UNKNOWN_EVIDENCE` 表示引用不属于本次证据包。格式合法但温度错误仍会被拒绝。

自由文本 `summary` 的每句话没有被全面验证。因此“关键字段通过”不能写成“生成完全正确”。这条命令也不会执行建议；模型接入与动作执行是独立步骤。

<a id="lesson07--练习"></a>

### 练习

在人工样本副本中添加 `approved: true`，再把摘要改为“设备已修复”。前者应被结构校验拒绝；后者可能通过有限字段检查。说明为何还需要陈述支持评价、人工审核或更受限的生成格式。

## 第 08 课　受控动作与对账

目标：完整观察提案、可信批准、幂等执行、响应丢失与跨进程恢复。对应书籍第 11、13、17 章。

<a id="lesson08--正常执行与响应丢失"></a>

### 正常执行与响应丢失

```console
python -m ontology_lab actions --scenario normal
python -m ontology_lab actions --scenario timeout
```

每次默认使用新目录。正常场景首次与重试都返回 `executed`。超时场景首次为 `outcome_unknown`，同键重试仍未知，对账后为 `executed`。两个独立演示各自只创建 1 份外部草稿。

注意 `proposal.state: awaiting_approval` 是初次创建时返回的提案快照；演示随后由可信合成计划员进行批准。输出不是模型自行批准的过程。

<a id="lesson08--分两个进程恢复"></a>

### 分两个进程恢复

先停在未知状态，并保存报告。目录名必须尚未用于动作演示：

```console
python -m ontology_lab actions --scenario timeout --no-reconcile --workdir .runs/action-step --output .runs/action-step/result.json
```

此时 `final.state` 仍未知，但外部模拟系统已经有一份草稿。Windows PowerShell 可读取操作 ID，再启动新的对账进程：

```powershell
$actionRun = Get-Content -Raw -Encoding UTF8 .runs/action-step/result.json | ConvertFrom-Json
python -m ontology_lab reconcile --workdir .runs/action-step --operation ($actionRun.first_attempt.operation_id)
```

其他环境可从 JSON 中复制 `first_attempt.operation_id`，替换下面的占位值：

```console
python -m ontology_lab reconcile --workdir .runs/action-step --operation OP-REPLACE-WITH-ACTUAL-ID
```

预期返回 `state: executed` 及 `receipt.status: DRAFT`。再次对账仍取得同一回执。

<a id="lesson08--解释"></a>

### 解释

提案绑定对象版本、观测、程序内容哈希和策略。批准绑定提案及有效期。首次写入之前，系统复核当前状态；外部模拟器也检查其对象版本，避免读取与写入之间的数据变化被忽略。

本地请求幂等避免相同请求重复派发，同提案唯一性避免通过换键重复执行，外部请求 ID 用于确认实际效果。若外部提交成功但网络响应丢失，系统必须承认“结果未知”，不能直接判定失败后重发。

动作记录与外部模拟器分别使用独立 SQLite 文件。重启 `ActionService` 后状态仍存在，体现的是持久化机制；它不是跨机高可用系统。

<a id="lesson08--常见失败"></a>

### 常见失败

`RUN_EXISTS` 保护已有记录。要学习重试，使用原服务状态与请求 ID；要重跑全新演示，使用新目录。`RUN_MISSING` 表示对账没有指向已有动作目录。

批准失效、对象版本变化、文档变化或只读身份都应阻止首次写入。已确认成功的记录不能被晚到的未知结果覆盖。相关反例已经包含在测试中。

<a id="lesson08--练习"></a>

### 练习

解释为什么本地请求表去重仍需要外部幂等或对账。再设计“两个不同提案对应同一次异常”的案例：现有同提案去重不够，需要业务事件 ID、活动工单唯一约束或人工合并策略。

## 第 09 课　评估与反例

目标：从原始案例计算指标，并说明结果可以支持哪些结论。对应书籍第 14 章。

<a id="lesson09--操作"></a>

### 操作

```console
python -m ontology_lab evaluate --output .runs/evaluation.json
python -m unittest discover -s tests -v
```

第一条输出四个检索案例和两个防护案例；第二条运行本版 40 项行为测试。HTTP 适配器测试会启动只在回环地址监听的临时测试服务，结束后关闭，不调用真实模型。

<a id="lesson09--预期结果"></a>

### 预期结果

| 检查 | 本版实测 |
| --- | --- |
| 词项检索 Hit@1 | 2 / 4 = 0.5 |
| 程序关系辅助 Hit@1 | 4 / 4 = 1.0 |
| 区域越权案例 | NOT_FOUND_OR_FORBIDDEN |
| 过期数据案例 | needs_information |
| 真实模型调用 | 0 |
| 生产业务系统调用 | 0 |

查看[evaluation-cases.json](../../tutorials/ontology-ai/data/evaluation-cases.json)，逐条对照 `expected_document` 与实际返回列表。报告中的 `cases` 是检索案例分母，不应把两个防护案例加入这个分母。

<a id="lesson09--解释"></a>

### 解释

四个检索案例是人工设计的机制实验；两个方法都得到显式资产编号。结果不评价实体链接、向量检索、模型事实正确率或生产延迟，也不是独立抽样基准。

40 项测试覆盖具体契约，例如 domain 推断、跨租户身份、错误字段、缺失观测、批准过期、条件版本变化、外部响应丢失及回执不匹配。测试名称和断言是行为说明，不能当作真实用户规模或防御覆盖率。

报告保存 Python、依赖版本和实现摘要。修改实现后，旧结果不能继续冒充新版本实测。固定业务时钟用于复现，`executed_at` 用于记录实际执行时点。

<a id="lesson09--常见失败"></a>

### 常见失败

把 `hit_at_1: 1.0` 说成“大模型准确率 100%”混淆了任务、样本和系统组件。删除难例后总分升高也不能证明改进。调参时使用过的案例应标为开发集，另准备独立评估集。

<a id="lesson09--练习"></a>

### 练习

给评估集设计四条新场景：关系缺失、关系过期、名称歧义、程序被撤回。分别说明正确答案、应拒答条件和需要改变的组件。先写标签再调算法，避免按现有结果反向定义成功。

## 第 10 课　迁移与综合项目

目标：完成一次可重复迁移，运行完整工作流，并形成自己的交付说明。对应书籍第 16—18 章。

<a id="lesson10--迁移操作"></a>

### 迁移操作

```console
python -m ontology_lab migrate --workdir .runs/migration-lesson
```

查看[migration-v1.ttl](../../tutorials/ontology-ai/data/migration-v1.ttl)与[更新语句](../../tutorials/ontology-ai/queries/migrate-v1-v2.ru)。首次 `moved_edges` 为 1，再次为 0，旧关系剩余为 0。输出图保存为 `migrated.ttl`。

示例把 `legacyAsset` 改成 `forAsset`，并把旧谓词标为弃用。文件名的 v1/v2 是迁移前后样例名称；本体版本由样例的 `0.9.0` 更新为本教程基线 `1.0.0`，不是声称发布了领域本体 2.0。

这里每次命令从旧样例读取，再在内存里连续执行两遍迁移；它演示转换幂等，不是在线数据库迁移服务。真实迁移仍需检查点、备份、兼容读写及恢复方案。

<a id="lesson10--完整运行"></a>

### 完整运行

```console
python -m ontology_lab demo --workdir .runs/my-capstone
```

目录必须是新目录。依次检查 `demo-report.json`：单位转换为 72 C；预期推理为真；有效与错误数据分别通过和拒绝；程序文档正确；响应丢失后对账成功且草稿数为 1；评估与迁移结果符合预期。

完整案例使用规则基线，不会自动调用第 07 课的真实模型，也不会将之前单独生成的结果自动送入动作服务。这使默认案例具有可重复行为。扩展时应显式传递经过验证的建议，并重新验证批准与动作边界。

<a id="lesson10--交付一页说明"></a>

### 交付一页说明

完成课程后，写出你的任务、使用者、输入数据、概念关系、正常结果、失败结果、指标、未实现项和下一步验证。记录实际运行环境、源码版本、数据版本及结果目录。

至少回答：为何需要本体；哪些行为由查询完成；哪些由逻辑推理完成；哪里调用了模型；谁批准动作；如何确认外部结果。若某项没有实际发生，应如实写明。

<a id="lesson10--常见失败"></a>

### 常见失败

将应用回滚等同于撤销外部工单，是恢复设计中的错误。迁移后忘记重建派生图、索引或缓存，也可能继续返回旧语义。只验证文件能解析，不足以说明关键能力问题仍成立。

<a id="lesson10--结课练习"></a>

### 结课练习

加入一种新观测，例如振动值。先定义单位、时效、设备关系和能力问题，再决定是否扩展建议合同与动作前提。至少准备正常、缺失、单位未知、过期与越权五种样本。

在结果说明中保留原温度实验与新增振动实验的分界，不把未测功能写成已实现。若新增模型诊断或真实写入，应另行建立领域审核与完整评估。
