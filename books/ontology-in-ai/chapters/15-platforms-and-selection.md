# 第 15 章　平台、工具与选型

本章目标是把工具放回系统职责中。不同工具处理建模、存储、逻辑、校验、检索或业务操作，名称中都出现“图”或“本体”并不意味着可以直接互换。

## 15.1 先判断需要哪种语义能力

如果需求是统一字段解释与少量关联查询，关系数据库加数据字典也可能足够。如果需要共享词汇、跨来源身份、可交换图数据和明确逻辑语义，RDF 与 OWL 工具链更有吸引力。如果团队主要进行关系遍历、图算法与应用开发，属性图可能更适合现有技能。

若目标还包括业务对象应用、受控动作和平台治理，就应评估完整业务平台。采购一个图数据库，并不会自动获得组织流程、权限传播、用户界面或动作恢复。

## 15.2 核心工具的职责

| 工具 | 主要职责 | 适合本书中的工作 | 需要单独核对的边界 |
| --- | --- | --- | --- |
| Protégé | OWL 本体编辑、浏览与扩展 | 类层级、公理、命名与人工评审 | 推理器插件、协作方式、版本管理；不是业务执行平台 |
| RDFLib | Python 中解析、构造、查询 RDF | 小规模原型、导入、教学、嵌入式处理 | 存储插件与数据规模；Python 库不等于托管数据库 |
| OWL-RL | 基于规则扩展图 | 受限推理与机制实验 | 不等于完整 OWL 2 DL 推理和证明服务 |
| pySHACL | SHACL 校验 | 数据合同、候选图质量检查 | 显式指定推理与高级功能；检查复杂度受形状影响 |
| Apache Jena / Fuseki | Java RDF 工具链与 SPARQL 服务 | 服务化查询、规则推理及存储集成 | 各推理配置的覆盖范围、部署与权限安排 |
| GraphDB | RDF 数据库及规则推理 | 需要数据库级 RDF 工作流的项目 | 规则集、版本、许可、集群与运维选项 |
| Neo4j | 属性图存储与查询 | 面向关系遍历的应用与图分析 | RDF/OWL 语义需额外建模或组件，不能从存储结构自动获得 |

这些定位依据相应项目文档，不是性能排名。[R18](../references/README.md#r18) [R19](../references/README.md#r19) [R20](../references/README.md#r20) [R21](../references/README.md#r21) [R22](../references/README.md#r22) [R23](../references/README.md#r23) [R24](../references/README.md#r24) [R37](../references/README.md#r37)

本书运行锁定 OWL-RL 7.1.4，但本次读取的文档页面标题仍显示 5.2.2；因此具体行为以锁定环境和测试为准。GraphDB 阅读范围为 11.0 文档，也不应自动外推到其他版本。

## 15.3 Palantir Ontology 的工程含义

Palantir 把 Ontology 定位为连接数据、业务对象及其操作的平台层。对象类型、属性、链接类型和动作类型把数据映射为业务可使用的概念与交互。[R33](../references/README.md#r33) [R34](../references/README.md#r34) Action Types 描述对对象、属性或链接等执行变更的操作。[R35](../references/README.md#r35)

它与本书 RDF/OWL 路线共享“显式业务概念”的思想，但不能因此推定 Foundry Ontology 就是 OWL 文件、默认执行 OWL 蕴含，或所有能力都能通过 RDF 导出保留。平台对象模型、操作模型和 W3C 标准逻辑语义需要分别对照。

设备案例可作如下映射，具体配置应在客户租户与许可范围内验证：

| 本书概念 | 在 Foundry 中需要设计的内容 |
| --- | --- |
| 设备与观测 | 对象类型、属性、主键、源数据映射及更新规则 |
| 设备—产线—厂区 | 链接类型、业务基数、可访问范围 |
| 维修程序 | 文档或相应对象、版本、适用范围及有效期 |
| 创建维修草稿 | 动作类型、参数、提交条件、权限和具体变更 |
| 外部工单系统 | 接口集成、请求标识、回执、幂等与对账责任 |
| 模型建议 | 受控上下文、输出合同、评估及人工审核界面 |

平台内动作成功与外部系统写入成功之间，仍要建立明确的完成定义。访问控制传播也有具体边界，尤其要检查读时过滤、派生输出和外部应用的处理。[R36](../references/README.md#r36) 本教程没有连接 Foundry，表格是设计映射，不是已完成平台部署的报告。

## 15.4 GraphRAG 与本体编辑器解决不同问题

Microsoft GraphRAG 的索引流程包含从文本构造图以及生成相关摘要等步骤；其研究讨论了面向语料整体问题的图辅助查询与摘要路线。[R25](../references/README.md#r25) [R26](../references/README.md#r26) 这与设备维修中“沿已维护程序关系读取特定文档”的任务不同。

文本抽取图常带有不确定的实体、关系和社区摘要。业务本体则需要明确身份、概念及责任。可以把抽取图作为候选知识来源，但不应直接当作已审核的业务对象库。选型时先写明是局部对象查询、全局主题总结，还是需要修改业务状态。

本书只核读 R26 的出版机构摘要页，未复现论文实验。不能用论文描述的结果替代本项目的评估。

## 15.5 模型层应保持可替换

无论模型来自本地还是托管服务，建议把访问包、结构化输出、校验和动作服务分开。替换模型时复用相同评估集，检查缺失值、拒答、引用、字段正确性及成本。

教程使用 Ollama 的 `/api/generate` 接口作为可选适配器，发送 JSON Schema 并关闭流式输出。[R30](../references/README.md#r30) [R31](../references/README.md#r31) 文档注明 Ollama Cloud 暂不支持结构化输出；本教程默认面向本地服务。没有服务时，基线与人工样本模式仍可学习其余机制，但不能用于评价模型质量。

## 15.6 用小型选型实验代替功能清单打分

拿同一份代表性数据完成五件事：导入并保留来源；回答能力问题；拒绝越权与错误输入；处理一次模式迁移；在故障后恢复一次业务请求。记录每项的实现工时、运行成本、延迟、查询表达难度和运维要求。

同时实际导出数据、查询、模型定义和评估资产，检查能否在目标路线恢复。所谓“支持开放格式”需要落实到对象身份、时间、权限和动作语义是否保留。

总拥有成本至少包括许可或云费用、数据工程、建模与审核、平台运维、培训、变更和退出成本。报价和产品能力随版本及合同变化，本书不编造统一价格，也不提供脱离工作负载的“最佳数据库”。
