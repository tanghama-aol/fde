# 第 17 章　设备维修助手完整案例

本章把前面的概念连接成一次可运行交付。所有数据均为合成数据，业务动作写入本地模拟器。读者应同时观察结果、约束和失败状态。

## 17.1 问题与验收

北厂计划员输入设备编号 `P-101`。系统需要定位当前租户和厂区内的设备，读取最新观测与对象版本，找到有效程序，生成有证据的建议，经批准创建维修工单草稿。

| 情况 | 期望行为 |
| --- | --- |
| 北厂 P-101，92 C，程序有效 | 提出需批准的维修草稿建议 |
| 北厂 P-102，161.6 F | 转换成 72 C，本教学规则下不建议建单 |
| 同名但属于另一租户的 P-101 | 只按可信身份访问相应租户 |
| 北厂身份请求南厂 P-201 | 返回不存在或无权访问，不暴露详情 |
| 观测或对象快照过期 | 请求补充信息，停止提出写入动作 |
| 外部已创建，但返回响应丢失 | 保持未知，通过同请求 ID 对账恢复 |

80 C 只是本教学案例的核查阈值。真实设备的报警标准、程序与人员资格必须来自其领域规则。

## 17.2 数据模型与服务边界

核心类包括设备、泵、离心泵、产线、厂区、观测和程序。每次观测是独立对象，保存时间、单位和值。租户与设备编号共同组成身份，设备名称只供展示。

系统由五个逻辑部分组成：CSV 到 RDF 的导入器；提供授权上下文的图服务；选择文档的检索器；生成和验证建议的组件；保存提案、批准、执行请求并连接外部模拟器的动作服务。

```text
CSV + 本体 ─→ 命名图 ─→ 身份与区域检查 ─→ 当前观测和关系
                                               │
程序文档 ─→ 权限与有效期过滤 ────────────────────┤
                                               ↓
                                         本次证据包
                                               ↓
                                   基线 / 样本 / 可选本地模型
                                               ↓
                                   输出合同与关键字段校验
                                               ↓
                                   提案 → 批准 → 条件执行
                                               ↓
                                   外部草稿回执 / 未知后对账
```

OWL RL 的类型、逆关系与传递关系演示独立展示逻辑蕴含；应用检索本身使用固定关系查询和有界遍历。不能把所有图遍历收益都归为 OWL 推理收益。

## 17.3 从干净环境启动

安装方式见[教程入口](../../../tutorials/ontology-ai/README.md)。完成环境准备后，在 `tutorials/ontology-ai` 目录运行：

```console
python -m ontology_lab doctor
python -m ontology_lab demo
```

默认创建新的 `.runs/demo-...` 目录，报告包含导入、推理、校验、检索、动作、评估和迁移。也可以使用 `--workdir` 指定新目录。已有完整案例目录不会被清空；再次运行时换一个目录，以保留原始执行记录。

基础案例不调用模型。要学习模型输出验证，运行 `generate --mode fixture`；要评价实际模型，另行准备本地 Ollama 服务并使用 `generate --mode live --model 模型名`。三种模式的含义和实测范围必须分开。

## 17.4 阅读一次正常证据链

P-101 的证据包包含租户 `TENANT-A`、区域 `NORTH`、对象版本 7、92 C 的观测及其时间，图证据 ID 为 `KG:TENANT-A:P-101:v7:OBS-101`。适用程序是 `PROC-PUMP-01`，授权文档是 `MANUAL-N-1`。

文档内容哈希绑定本次使用的程序文本。提案保留设备、温度、时间、程序、证据、文档哈希与策略版本。批准是可信计划员对该具体提案的授权，模型输出的 `requires_approval` 只是建议合同字段。

首次写入前，动作服务复核身份、批准、对象状态、新鲜度和程序。外部模拟业务系统也按其当前对象版本执行条件写入，避免应用读取后、写入前出现变化却仍盲目接受请求。

## 17.5 亲自观察响应丢失

运行：

```console
python -m ontology_lab actions --scenario timeout
```

报告中，`first_attempt.state` 为 `outcome_unknown`，`same_key_retry.state` 仍为 `outcome_unknown`，对账后的 `final.state` 为 `executed`。外部草稿总数是 1。重复提交没有将“不知道结果”直接改写成“重新创建”。

通过第 08 课的分步命令，还可以停止在未知状态，再由新的进程打开原目录进行对账。执行记录与外部草稿分别存放在不同 SQLite 文件中，用来展示状态持久性与跨系统响应不确定性。

`executed` 只表示该草稿动作取得匹配回执。它不表示正式派工、设备已经停机或故障已修复。若两个不同提案实际上对应同一次异常，还需要额外的异常事件唯一键，当前同提案去重不会自动解决这个业务问题。

## 17.6 实际得到的结果

在锁定环境中，原始图有 125 条三元组，OWL RL 闭包为 451 条，增加 326 条；类型、逆关系和传递关系检查均通过。新增数量包含规则产生的语义相关三元组，不能解释为发现了 326 条新的业务事实。

有效数据通过 SHACL，故意错误的数据被拒绝；四个检索案例的词项基线命中 2 个，关系增强命中 4 个；超时对账最终只留下一份草稿；迁移首次移动一条关系，再次移动零条。完整原始报告和验证范围见[实测记录](../../../tutorials/ontology-ai/reports/verification.md)。

这些结果证明示例按既定合同运行。它们不证明工业诊断能力、生产吞吐量、模型正确率或完整的安全防御能力。本机验证没有调用真实模型或生产业务系统。

## 17.7 把案例迁移到自己的场景

先替换能力问题与评估样本，再替换数据映射。保持可信身份、来源、时间、证据包、输出合同及动作回执这些边界。若只是更换模型而没有定义领域含义，系统仍可能在正确格式里生成错误结论。

接入真实工单系统时，先确认其条件写入、幂等、请求查询和回执语义。没有请求查询能力时，要设计人工核对或业务事件查询路径，不能假设所有接口都像本地模拟器一样支持对账。
